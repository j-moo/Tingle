# 가상 키링 독립 처리 규격 — 0.13

2026-10-26 · Story S15P31E106-124 · IoT 시험 앱 전용. 버전 `0.13.0-lab`, 패킷 v4, SQLite v6. 실제 회원·서비스 등록·설정 동기화·서버 제출은 제외한다. 기존 0.12의 합의 규격과 비교 이력은 `VERIFICATION.md`와 작업 전 소스 백업에 보존한다.

## 계약과 최신 요청의 관계

작성 당시 기능 명세 `docs/specifications/functional-spec-v1.md`와 현재 [키링 통합 문서의 통신 명세](../KEYRING-SPEC.md#protocol)·[데이터 구조](../KEYRING-SPEC.md#data-structures)의 입력 필드·설정·저장 원본을 참고한다. 하지만 최신 사용자 요청은 **데이터 송수신 외 모든 처리는 각 기기가 독립 수행하고 매칭 후 근접 재확인을 제거**하는 것이다.

따라서 0.13은 원래 공통 이벤트·양쪽 저장 확인의 계약을 충족한다고 표시하지 않는다. 팀 문서는 변경하지 않는다. 새 이벤트는 내 관측 기록이며 `peerStorageVerified=false`, `productionUploadAllowed=false`다. 동일 이벤트를 양쪽에서 합의하는 서비스 연동이 필요해지면 별도 계약 검토가 필요하다. 수신 한 번으로 상대 판정·상대 저장까지 완료됐다고 추정하지 않는다.

## 무선 교환

양쪽 Android는 비연결 광고와 필터 스캔을 동시에 시작한다. 서비스 UUID는 `f8fd2a22-6039-4854-8897-70fcba711206`, 시험 그룹 AES-GCM·출처·대상·시각 검사를 유지한다. 그룹 공유키는 실험용이며 운영 기기 인증을 대체하지 않는다. 전파는 주변에 도달하지만 그룹이 다른 데이터는 해석·응답하지 않는다. 이번 버전에는 인증된 상대에게도 응답 패킷이 없다.

무선에서 보내는 타입은 v4 **PROFILE_BROADCAST(21)** 하나다. 아래 값이 하나의 인증된 본문에 들어간다.

| 데이터 | 내용 |
| --- | --- |
| 내 정보 | 합성 회원 UUID, 키링 UUID, 설정 snapshot UUID, 설정 버전, 준비 여부 |
| 설정 | 매칭/알림 ON, 사진 등록 여부, 사진 없는 상대 제외, 정책·규칙 버전, 기회 유지 기간 |
| 임시 성향 | 나이, 성향 5항목, 희망 성향 5항목 (0~100) |

기본 fixture는 최초 한 번 생성·저장하며 재실행 때 바꾸지 않는다. 임시 알고리즘은 성향·인구통계 판정을 항상 통과한다. 매칭 OFF·자기 자신·사진·준비·버전 일치 조건은 실제로 검사한다. 서버 관계 제한 목록은 아직 수신하지 않는다.

수신자 UUID는 broadcast(0), 대상 세션은 0이다. 자기 송신을 제외하며 봉투 출처 UUID와 본문의 키링 UUID가 일치해야 한다. 수신한 암호문은 180초 이내 과거/30초 이내 미래여야 한다. 반복 메시지는 nonce로, 완료한 판정은 입력 context/저장된 회원 쌍으로 중복 억제한다.

- 확장 광고: 기본 전체 본문 113바이트 + 인증 봉투 84 + 형식 1 + 서비스 식별 정보 18 = **216바이트**. 앱 상한 255, Android 갱신 상한 251 이내다. 1M PHY, non-connectable, non-scannable로 보내며 수신 스캐너는 확장 결과를 포함한다.
- 일반 광고: 같은 데이터를 7바이트 본문 조각 **29개**와 복구 조각으로 반복한다. 확장 지원 기기도 이 경로를 병행하므로 미지원 상대가 별도 협상 없이 수신한다.
- 확장 시작/갱신 실패 시 일반 경로를 유지한다. 지원 여부 API·실제 시작 콜백·전체 수신 로그를 구분한다. 컨트롤러 내부 PDU 분할 여부를 보장하지 않는다.
- `ProfileBroadcaster`에는 상대별 메시지 큐가 없다. 각 경로 데이터 갱신은 300ms, 같은 암호문 갱신은 확장 30초/일반 120초다. 이는 반복 탐색과 인증 freshness를 위한 송신이며 로컬 판정 대기 시간이 아니다.
- HELLO, PING/PONG, MATCH_RESULT, RECHECK/OK/BUSY, PREPARE/COMMIT/STORED/RECEIPT를 새로 보내지 않는다. 구형 타입은 기록 읽기·호환 테스트에만 남는다. 모든 참여 기기를 0.13으로 업데이트해야 한다.

## 세 가지 보관 상태

| 구분 | 들어오는 조건 | 나가는 조건 | 타이머 |
| --- | --- | --- | --- |
| 판정 FIFO | 완성·인증된 상대 데이터 | 차례가 비면 즉시 판정, 통과하면 내 저장 | 정상 작업의 지연·주기 없음 |
| 서비스 앱 전송 대기 | 내 DB에 원본·증빙 저장 완료 | 서비스 연동·서버 ACK 구현 전까지 보존 | 전송이나 자동 삭제 없음 |
| 오류 재처리 큐 | 판정 함수·작업 저장·만남 저장·알림 claim·작업 정리의 예외 | 실패 단계 성공, 또는 입력 기회 만료 | 실패한 항목만 1/2/4/8/16/30초, 이후 최대 30초 |

`IndependentMatcher`는 단일 작업 스레드에서 FIFO를 비울 때까지 처리한다. 현재 실패 작업은 오류 맵으로 분리한 뒤 다음 준비 항목을 같은 실행에서 처리한다. 점수·회원 ID 정렬이나 다음 후보를 위한 sleep은 없다. `LabController`는 오류가 있을 때 가장 이른 retryAt에만 타이머를 건다. 2초 UI 갱신은 큐 처리 계기가 아니다.

부분 수신은 위 세 큐와 별도의 **암호문 조립 버퍼**다. 최대 150초 수명 안에서 원본/복구 조각을 모으고 완성 즉시 처리한다. 임의로 150초 지연하지 않는다. 재조립 전에는 상대가 인증되지 않았으므로 잘린 평문을 알고리즘에 넣거나 정상 회원의 오류 작업으로 저장하지 않는다. 손상·인증 실패는 제외하며 다음 반복 광고로 새로 수신한다. 부분 암호문은 메모리 한정이고 OFF/프로세스 종료 시 없어지며, 인증된 실패 작업은 SQLite에 남는다. `RECEIVE_ASSEMBLY`는 10초당 최대 한 번 요약하고 조각 카운터는 계속 갱신한다. 이 로그 제한은 수신 처리 속도와 무관하다.

## 작업·원본·복구

`processing_jobs`에 입력 프로필 2개, context ID, 사전 할당한 로컬 eventId, receivedAt, matchedAt, 단계(MATCH/SAVE/FEEDBACK/DONE), attempts, retryAt, 오류 코드를 저장한다. 판정 전 입력을 저장하고, 이후 실패가 발생하면 입력·ID·진행 단계를 그대로 보존한다. 동일 입력을 다시 받아도 오류 재시도 기한을 초기화하거나 우회하지 않는다. 다른 상대는 계속 처리한다.

- 판정 성공 즉시 내 원본을 `CONFIRMED` 단계로 저장한다. **새 독립 기록의 CONFIRMED는 내 저장 완료만 뜻한다.** `independent=true`/DB `contract=2`로 구형 공통 이벤트와 구분한다.
- eventId는 각 기기가 독립 생성한다. 기준 시각은 해당 완전한 데이터를 처음 받아 작업에 넣은 시각이다. 실패 후 재처리가 원래 만남 기회를 연장하지 않는다.
- 같은 eventId의 다른 원본은 거부하고 submissionId·증빙을 보존한다. DB 저장 직후 예외가 발생해도 같은 ID로 다시 확인한다.
- 로컬 기록 타입 **LOCAL_RECORD(22)**는 SQLite 직렬화 전용이며 무선 송신하지 않는다. evidence protocol은 `virtual-keyring-local-observation-1`이고 합성 SHA-256 값이다. 실제 서버 검증용 서명이 아니다.
- DB 전체 쓰기 실패 시 큐 자체도 내구성 저장할 수 없으므로 `durable=false`를 로그에 남기고 실행 중 메모리에서 재시도한다. 이 경우 프로세스 종료 후 보존을 보장하지 않는다.
- 준비/오류 작업 합계 128개, 만남 256개는 시험 한도다. 초과는 명시적 오류이며 기존 원본을 자동 삭제하지 않는다.

기존 확정 기록과 새 독립 기록은 같은 회원 쌍의 추가 기록·알림을 막는다. OFF·재시작으로 억제를 해제하지 않는다. 구형 미완료 PREPARED/COMMITTED는 원본 그대로 남기되 새 방식에서 양쪽 저장 완료로 승격하거나 구형 합의 통신을 재개하지 않는다. 서비스가 없으므로 서버 처리 완료·억제 해제를 임의로 만들지 않는다.

## LED·진동

내 저장 후 양쪽 **수신된 프로필의** 알림 플래그를 확인한다. 상대의 현재 위치나 저장 응답을 확인하지 않는다. 내 ON 상태·기한과 영속 feedback claim만 확인한다. 파형은 `[0,500,500,500]ms`, 진폭 `[0,255,0,255]`, 반복 없음이다. LED·흔들림도 같은 시작 기준이다.

`CLAIMED → STARTED → FINISHED` 또는 `STOPPED`, 설정/기한/OFF에 따른 생략 상태를 보존한다. 여러 상대 효과는 순서대로 재생하되 데이터 수신·판정·저장은 1.5초 효과 완료를 기다리지 않는다. claim 직후 프로세스가 종료된 경우 중복 방지를 우선하며 실제 진동 실행을 보장하지 않는다. 모터가 없으면 `NO_VIBRATOR`와 화면 효과로 구분한다. 두 기기 간 동시 진동을 보장하지 않는다.

## SQLite v6·JSON·로그

v5에서 v6은 별도 `processing_jobs` 테이블만 추가한다. 기존 identity·fixture·만남 원본·증빙·알림 상태·traffic를 재작성하지 않는다. v1~v4의 이전 마이그레이션도 v6까지 검증한다.

채팅 내보내기는 `virtual-keyring-independent-timeline-1`, 만남 내보내기는 `virtual-keyring-lab-4`다.

- `receivedMessages`: 인증된 수신 데이터 원문.
- `timeline`: DISCOVERY/TX/RX/PROCESS 로그. `LOCAL_QUEUED`, `LOCAL_EVALUATING`, `LOCAL_EVALUATED`, `LOCAL_SAVED`, `LOCAL_RETRY_WAIT`, `LOCAL_DUPLICATE`, 알림 상태가 분리된다.
- `localPending`: 내 독립 확정 기록과 원래 프로필·알림 상태. 상대 저장 미확인을 명시한다.
- `processingQueue`: 아직 처리 못한 작업의 입력·단계·오류·재시도 시각.
- `serverSubmissionPreview`: 예전 합의 방식의 확정 기록만 기존 8필드로 유지한다. 새 로컬 기록은 포함하지 않는다.

`LOCAL_EVALUATING.detail.queue_wait_ms`와 `LOCAL_SAVED.detail.receive_to_save_ms`로 로컬 처리 시간을 확인한다. 후자는 완전 수신 데이터가 매처에 들어간 시점부터 내 DB 저장까지이며, 무선 첫 조각을 기다린 시간은 포함하지 않는다. 값에는 SQLite 처리와 과정 로그 저장 시간이 포함된다. 채팅에서 해당 행을 누르면 JSON 상세를 볼 수 있다.

운영 기기 인증·서버 등록·동기화·성향 알고리즘·실제 서버 제출·ACK·원본 정리·관계 제한 갱신은 미구현이다. 담당자 간 합의 없이 이 시험용 독립 기록을 공통 서버 계약으로 취급하지 않는다.
