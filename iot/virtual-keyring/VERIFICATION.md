## 6대 실물 시험의 단일 기기 내보내기 검증 — 2026-10-26

참여 기기 6대 중 한 기기에서 받은 수신 타임라인과 만남 내보내기를 대조했다. 이번 시험 구간에서 상대 5대의 완전한 정보·설정·성향을 총 17회 수신했고, 판정 FIFO에 상대별 1건씩 5건을 넣었다. 4건은 독립 판정 통과·내 저장 완료 후 LOCAL_PENDING이며, 1건은 기존 확정 기록을 유지하여 PENDING_SERVICE_APP 상태를 보존했다. 새 4건의 판정 시작까지 4~7ms, 수신 후 내 저장까지 10~14ms였고 알림 상태는 모두 FINISHED다. 처리 오류·재처리 잔여는 없었다.

내 데이터의 216바이트 확장 광고 송신도 기록됐다. 나머지 5대에서 내 데이터를 수신·저장했는지는 이 두 파일만으로 검증할 수 없다. 따라서 6대 전체의 모든 방향 완료나 서비스 앱 전송·서버 접수를 확인한 결과로 해석하지 않는다.

## 자동 검사

- `:core:check` / `:core:verifyCore`: 아래 12개 시나리오 묶음 통과. JUnit 대신 실행형 Java 검증기를 사용하며 표준 `test/check`도 `verifyCore`를 실행한다. assertion 실패 시 프로세스가 실패한다.
- `:app:assembleDebug`, `:app:assembleDebugAndroidTest`: 성공.
- `:app:lintDebug`: 캐시를 제외한 재검사에서 오류 0, 경고 3. API 36 타깃 유지, 기존 검증 Gradle 버전 유지, API 31 미만에서 `neverForLocation` 속성을 무시하는 경고는 알려진 호환성 안내다. API 30 이하는 별도 위치 권한 분기로 처리한다.
- `checkstyleAll`: 네이버 규칙, 경고 0.
- `StorageInstrumentation`: Android 16(API 36)에서 실제 SQLite 재개방, 기기 ID·설정 사본·제출 ID 보존, 중복 방지, 충돌 롤백, SQL trigger로 주입한 쓰기 실패, 상태 후퇴 방지 통과. 테스트는 임시 DB를 사용한다.

## Android 두 인스턴스 통합 시험

환경: `DDUBI_API_36` AVD를 두 개의 읽기 전용·숨김 인스턴스로 실행, Android 16 / x86_64 / Emulator netsim Bluetooth. **가상 Bluetooth 전송이며 실제 삼성 기기 간 RF 시험이 아니다.**

1. 두 앱 설치 → Android ‘근처 기기’ 권한 요청·허용 확인 → 고정 시험 설정 저장.
2. B 광고 시작 성공 → A에서 발견 → 선택·GATT 연결 → indication 구독 → 양방향 HELLO 확인.
3. A의 PING/PONG 왕복 성공을 실제 화면의 최근 동작에서 확인.
4. A에서 수동 만남 생성 → 양쪽 기록 화면 `양쪽 저장 확인`.
5. Android 파일 선택기로 JSON 저장 → 파일을 가져와 JSON 구조·UTC 시각·`productionUploadAllowed: false` 확인.
6. `install -r`로 업데이트하여 앱을 재시작 → 기기·이벤트·제출 ID와 기록 보존 확인.
7. A/B 연결 역할 교환 → 다시 발견·연결 → 왕복 통신 및 기존 이벤트 재시도.
8. 양쪽 앱 전용 DB의 실제 행을 읽어 아래 결과를 대조.
9. 휴대폰 1080×2400 화면과 태블릿 형태 2000×1200 / 240dpi 화면에서 실제 렌더링·기록 표시 확인.

## S20+·S6 Lite에서 확인할 항목 — 아직 미실행

실제 두 기기가 PC에 연결되지 않아 다음은 사용 기기에서 수행해야 한다. 처음에는 S20+=A, S6 Lite=B로 진행하고 광고 지원에 따라 반대로도 시험한다.

| BLE 진단·광고 시작 | 각 OS 지원 보고와 실제 광고 시작 결과 구분 | 미실행 |
| A→B / B→A 왕복 | PING/PONG 성공, 상대 ID 확인 | 미실행 |
