# 키링 간 성향 교환·계산 개발 v1

2026-11-06 · IoT 김종무 · S15P31E106-226 · 펌웨어 `0.4.0-dev-peer`

후속 `0.5.0-app-flow`의 정상 앱 경로는 [전체 연동 v2](app-flow-v2-handoff.md)로 보강됐다. 아래 v1은 계산·PX 프레이밍·암호화의 기반 설명이다. v2는 새 TSV2/타입3 grant·공통 account ownerRef·관계 제한·만료·서명 기록 접수를 사용하며 v1의 196B 단독 저장을 전체 준비 완료로 취급하지 않는다.

상태: 로컬 구현·호스트 검증 대상인 개발 프로토콜이다. AI147/148의 최종 matchingVersion/운영 codec 승인, BE 관계 제한·폐기 credential 정책, 실제 보드 무선·MCU 수치 검증 및 공식 만남 접수 완료를 뜻하지 않는다. 사용자의 11월 6일 요청에 따라 **키링끼리 연결 없이 확장 광고와 수신으로 교환**한다. AI의 11월 3일 connected GATT 후보를 이 구현의 전제 조건으로 사용하지 않는다. 앱↔키링 NUS 연결은 계속 사용한다.

## 동작 순서

1. 앱이 등록 후 서버 서명 `tingle-profile-storage-v1` 196B를 암호화된 앱 BLE 특성으로 전달한다. 기존 1바이트 ON/OFF는 발견 진단만 지원하며 성향을 생성하지 않는다.
2. 기기는 서버 서명·nonce·소유 세대·설정 버전을 검증하고 기존 영역에 영구 저장해 STORED를 반환한다. `LAB ENABLE`는 필요 없다. FE는 기존 서버 ACK를 별도로 제출한다.
3. 저장 응답 전송 성공 후 해당 부팅/동기화의 새 X25519 임시 키와 기기 서명 증명을 사용해 확장 광고·수동 스캔을 병행한다. 앱 연결 유지 여부는 peer 교환의 조건이 아니다.
4. HELLO에서 임시 공개키만 발견한다. 상대별 키를 파생해 AUTH를 암호화 교환한다. AUTH에는 기존 서버 서명 설정의 결속 정보와 임시 공개키를 결속한 기기 서명이 있으며 **성향 원문은 없다**.
5. 고정 서버 공개키·기기 공개키·기기 서명·자기 기기/소유 세대가 아님을 확인한 상대에게만 PROFILE을 암호화 광고한다. 수신 payload 해시는 해당 서버 증명의 해시와 같아야 한다.
6. 양쪽이 자기/상대 스냅샷으로 두 방향을 독립 계산한다. FIFO 알고리즘 큐를 바로 처리하고 기존 확정/검증 대기 큐에 영속 기록한다. 양방향 제어 단계도 같은 상대별 암호화 광고로 진행한다.
7. 같은 이벤트의 재전송은 허용하고 반복 확정/알림은 억제한다. PROFILE과 제어 패킷을 번갈아 보내 한쪽이 아직 PROFILE을 받지 못한 경우에도 진행된다. 다른 쌍의 목적지 패킷은 BT 콜백에서 걸러 RX 큐를 보호한다.

`matchingEnabled=false` 저장, 초기화, 저장 오류에서는 새 교환을 중지한다. 전원 재시작 시 저장 설정/기록은 복원하지만 신뢰 시간이 없으므로 새 서명 동기화 전 peer를 재개하지 않는다. 임시 키·인증 세션은 플래시에 저장하지 않는다. 기기 고유 인증키·serial·NVS 영역/기존 레코드 ABI는 변경하지 않는다.

## 계산 기준

원본은 `ai-server/reference/survey-20261021/mockup/dist/engine100.mjs`이며 외부 r2의 원본과 SHA-256이 같다:

`1b45d79d88b90bc407170acab69b32e29ad1efbf034fdb8536128a3051436893`

- 구현: `src/matching.c`, 선언: `include/matching.h`. 196B decoder는 `src/profile.c`를 재사용한다.
- E/A/C/I는 저장된 scale100 정수를 double로 해석한다. 구간/범주/복수 선택 적합도를 영역별 평균 후 Q96 선택 영역 가중치 2, 나머지 1로 계산한다. Q87은 양쪽 실제 시간대의 불일치를 관측 0점으로 우선 처리하며 irregular만 남는 경우와 구분한다. Q89의 하한 1 규칙을 유지한다.
- 각 방향 점수 ≥50, 커버리지 ≥0.7, 엄격 제외/미해결 없음이 참조 판정 조건이다. 조화평균도 계산하지만 한 방향 미달을 조화평균으로 구제하지 않는다. 이는 **고정 PC 기준을 이식한 개발 값**이며 운영 임계값 최종 승인으로 바꾸지 않는다.
- 정보가 없으면 점수는 미계산 상태이며 0점으로 채우지 않는다. Q98 미확인, Q96/Q97 미확인은 임의 기본값 대신 계산 보류/검증 큐로 간다.
- 제품 기본 조건은 별도 검사한다: 양쪽 매칭 ON, 성인 나이/희망 범위, 현재 MVP의 반대 성별·단일 대상 성별, 양쪽 사진 요구 조건. unknown을 OFF/상관없음으로 바꾸지 않는다. 나이 상한 없음과 ANY를 구분한다.
- 개발 엔진 내부 policy=`0x52504331`, rule=`0x10001101`은 로컬 호환성 구분자다. 서버/AI가 승인한 release나 matchingVersion이 아니다. 기존 Lab의 항상 매칭은 합성 전용 경로에 남긴다.

## 광고 형식과 암호화

개발 전용 서비스 데이터 UUID: `8e8c0007-67a0-4d2f-9c17-120b4c80e106`. 기존 Lab UUID와 NUS UUID는 유지한다. 키링 peer 연결을 만들거나 connected MTU에 의존하지 않는다.

각 AD service-data는 UUID16B + CRC32/전체 길이/offset(8B) + 최대230B 조각이다. 하나의 확장 광고 이벤트에서 여러 AD 필드를 묶고 Zephyr의 AUX_CHAIN 재조립 결과를 사용한다. 조각 누락·순서/길이/CRC 오류는 정상 메시지로 처리하지 않는다. 광고 간격은 기존 BLE radio 설정이며 큐 대기 시간이 아니다.

내부 wire header(78B):

| offset | 길이 | 값 |
| --- | ---: | --- |
| 0 | 2 | ASCII PX |
| 2 | 1 | 버전 1 |
| 3 | 1 | HELLO=1, AUTH=2, DATA=3 |
| 4 | 32 | 발신 X25519 임시 공개키 |
| 36 | 32 | 목적지 임시 공개키. HELLO는 0 |
| 68 | 8 | little-endian 송신 sequence. HELLO는 0 |
| 76 | 2 | 암호화 평문 길이. HELLO는 0 |

AUTH/DATA는 header를 AAD로 하는 XChaCha20-Poly1305 ciphertext + 16B MAC을 붙인다. X25519의 all-zero 공유값은 거부하고, BLAKE2b-256으로 `16B domain(TINGLE-PEER-KDF1 + NUL) || shared32 || sourcePublic32 || destinationPublic32`를 해시해 방향별 키를 파생한다. nonce24B는 선행16B=0, 후행8B=sequence다. sequence는 부팅 중 stop/retry에도 유지해 같은 키의 nonce를 재사용하지 않는다. 새 부팅은 새 서명 동기화·CSPRNG 임시 키가 필요하다. 수신 counter 이하 재전송은 변경 없이 거부한다.

사용 라이브러리의 계약은 [Monocypher AEAD](https://monocypher.org/manual/aead), [X25519](https://monocypher.org/manual/x25519)를 따른다. 새 peer wire/인증 조합 자체의 운영 보안 승인을 뜻하지 않는다.

AUTH 평문(325B)은 기존 서명 원문의 무손실 바이너리 표현이다:

| offset | 길이 | 값 |
| --- | ---: | --- |
| 0 | 1 | 서버 proof v1=1/v2=2 |
| 1 | 8 | XIAO serial의 hardware hex 원본 |
| 9 | 8 | 서버 deviceId |
| 17 | 4 | settingsVersion |
| 21 | 8 | ownershipEpoch. v1은 0 |
| 29,45 | 각16 | ownerGeneration, syncRunId UUID |
| 61,93 | 각32 | nonce, deviceNonce의 Base64url 복호화 원본 |
| 125 | 8 | 서명 원문의 serverTime epoch초 |
| 133 | 32 | 원본 196B의 SHA-256 |
| 165 | 32 | 기기 Ed25519 공개키 |
| 197 | 64 | 기존 서버 설정 서명 |
| 261 | 64 | `TINGLE-PEER-AUTH-V1\n` + 발신 임시 공개키32 + 앞선261B에 대한 기기 서명 |

수신자는 고정 팀 서버 키로 기존 14줄(v2는 epoch 추가) 원문을 재구성·검증한다. serial은 `XIAO-`+16자리 소문자 hex, keyId는 `ed25519-`+기기 공개키 첫8B hex다. 현재 XIAO 생성 규칙과 다르면 우회하지 않는다. 버전은 현재 엔진의 uint32 범위를 넘으면 PEER_SETTINGS_UNSUPPORTED로 거부하며 소유 epoch와 서버 deviceId의 int64 양수 범위를 유지한다. 수신 시 serverTime이 현재 신뢰 시각보다 300초를 초과해 미래이면 거부한다. 별도 credential 만료/폐기 정책은 아직 공급되지 않았으며 300초를 큐 TTL이나 설정 만료로 사용하지 않는다.

DATA 평문은 기존 내부 엔진의 PROFILE(248B) 또는 제어(75B) 패킷이다. PROFILE의 196B hash·revision·policy/rule·snapshot 결속을 확인한 후에만 엔진에 전달한다. 위 CRC는 무선 조각 진단용이고 인증 근거는 서버/기기 서명 및 AEAD다. 공개 광고에 성향·프로필·기기 serial을 평문으로 넣지 않는다. 상대에게도 이름/생년월일/사진/토큰/원본100문항/관계 제한 목록을 전송하지 않는다. 서버 설정이 서명한 196B를 그대로 교환하므로 필드 선택적 공개 계약이 필요한 경우에는 BE/AI와 별도 형식이 필요하다.

## 다중 상대·큐·저장

- 동시 세션 캐시 16개. 두 대로 제한하지 않는다. HELLO/AUTH/PROFILE/control을 상대별 round robin으로 광고하고 수신·계산은 도착한 완성 입력 순서대로 바로 처리한다.
- 인증되지 않은 HELLO는 인증 세션을 밀어내지 못한다. 캐시가 찼을 때 최근 30초 동안 유효한 암호화 통신이 없었던 가장 오래된 세션 키만 회수할 수 있다. **이 30초는 발견 캐시 회수 기준이며 3개 큐의 체류 시간·만남 만료가 아니다.** 다시 발견되면 재인증한다. 영속 기록은 지우지 않는다.
- 기존 알고리즘 대기8, 확정12, 오류/검증12 및 영속 슬롯32를 유지한다. 자료 부족·실패·버전 충돌은 검증 경로로 보존한다. 인증된 peer가 MAC 검사를 통과한 뒤 잘못된 DATA를 보낸 경우만 오류 증거를 남긴다. 공개 무선 쓰레기로 플래시를 채우지 않는다.
- 저장/수신 공간이 부족하면 overflow/backpressure로 표시하고 유효 미접수 원본을 덮어쓰지 않는다. 확정/검증 기록은 앱이 읽거나 상대가 사라졌다는 이유로 삭제하지 않는다.
- 재부팅/새 동기화 후에도 기존 이벤트는 보존해 중복 알림을 막는다. 기존 합성 owner와 현재 서명 owner가 다른 내부 저장소는 자동 삭제/양도하지 않고 peer 시작을 보류한다.
- 정상 프로필 모드에서는 기기에 저장된 LED 옵션을 확인한다. 외부 진동 모터 배선을 추측해 활성화하지 않는다. 실제 알림 회로/색/버튼 UX 검증은 별도다.

## FE·BE에서 필요한 연결

앱/서버의 **196B 공급·서명·보호 특성 중계**는 [기존 인계 문서](dev-settings-signing-handoff-v1.md)의 작업이 여전히 필요하다. 이번 peer AUTH는 그 정상 서버 서명과 기기 인증키를 재사용하므로 별도 서버 개인키나 보드별 UF2를 요구하지 않는다. 서명 없는 앱 프로필을 끼워 넣지 않는다. DEVICE_INFO에는 peerExchangeProtocol/maxPeerSessions를 추가하며 이는 지원 능력이다. applied/timeReady는 전체 제품 준비를 뜻하는 true로 올리지 않는다.

196B에는 로컬 관계 제한/폐기 목록이 없다. 따라서 차단·활성 채팅·서버 제안 상태 등 **운영 정책을 완전히 반영한 매칭**은 아직 아니다. 서버가 발급할 opaque ownerRef/peerRef·자격 폐기/제한·시간/정책 버전, 공식 만남 서명·NUS 기록 업로드·서버 접수 영수증 계약을 연결해야 한다. 현재 내부 확정 기록을 정식 서버 검증 가능한 만남으로 제출하지 않는다. 초기화의 미전송 수에는 내부 확정/검증 대기가 포함되므로 임의 초기화로 지우지 않는다.

## 검증·실물 시험

- `tools/test-host.ps1`은 기존 엔진/등록/서명/초기화 검사 뒤 `tools/test-peer.ps1`을 실행한다. 공개 합성 시험키만 사용하며 이 키들은 제품 CMake 소스에 포함하지 않는다.
- 10개 가상 C 키링의 상호 인증·암호화 광고, 양방향 계산, 손실/중복/변조/재전송, 3개 큐, 재부팅 후 새 세션/기록 보존/반복 알림 억제, 미인증 캐시 압박을 확인한다. 실물 RF 혼잡 시험과 구분한다.
- `tools/verify-peer-golden.py --handoff <기존외부폴더> --runner <build/tests/peer/test-peer.exe> --output <build/tests/peer/golden>`로 원본 hash를 확인하고 독립 C 결과를 비교한다. 4개 핵심 + 33개 r2 지원 비교가 1e-8 이내 일치했다. 미지원 버전2·잘못된 입력2·정책 미확인1·원본에서 건너뛴1 사례를 분리했다. 같은 원본이 핵심/r2에 중복될 수 있으므로 37개 고유 실물 사례라고 부르지 않는다.
- 실제 보드·Android/서버 종단·재부팅 키 보존·확장 광고 유실/혼잡·연산 전력·MCU 점수 오차·장시간 시험은 미실시다. USB 진단은 peer proof/exchange/rejected 누적 수를 출력하며 실제 성향 내용이나 개인키를 출력하지 않는다.
- 실물은 기존 키를 유지한 동일 UF2를 사용한다. 2대부터 등록→새 형식 동기화→STORED/서버 ACK→peer 증명/교환→같은 양방향 결과→중복 억제→OFF→재부팅 후 재동기화 순서로 검사하고 이후 10대로 확장한다. 현재는 실제 보드 쓰기를 하지 않았다.
