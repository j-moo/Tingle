# 가입과 매칭의 앱 개발 기준

| 항목 | 내용 |
| --- | --- |

이 문서는 앱의 가입부터 매칭 제안과 채팅 진입까지 연결하기 위한 기준이다. 사용자가 결정한 흐름을 우선 반영하고, 입력값과 상태 이름은 검토 가능한 초안으로 제시한다. 지금은 앱의 틀을 먼저 만들며 문항·가중치·추천 기준 개선은 후속으로 분리한다.

## 1. 결정 사항과 임시 사용 범위

| 구분 | 기준 |
| --- | --- |
| 확정된 흐름 | 구글·카카오·네이버 로그인 → 키링 등록 → 본인 프로필 → 성향테스트 → 희망 성별·나이 설정 → 준비 상태 확인 → 서비스 이용 |
| 키링 등록 | 등록한 회원만 프로필 이후 단계로 진행한다. 미보유자는 구매 링크를 제공하되 구매 링크 방문·결제만으로 등록 완료 처리하지 않는다. 등록 실패는 재시도 경로를 제공한다. |
| 매칭 방향 | 성향테스트를 바탕으로 매칭하고 희망 성별·나이는 별도 기본 조건으로 설정한다. 키링 설정의 사진 필수 옵션은 점수와 별도인 대상 제외 조건이다. 생활 조건 하나가 다르다는 이유로 무조건 제외하는 기존 설계는 사용하지 않는다. |
| 프로필과 채팅 | 유효한 매칭 제안의 당사자는 수락·거절 전에 상대의 공개 프로필 전체를 확인한다. 채팅 입장·메시지 전송은 상호 수락 이후에만 허용한다. |
| 사진 입력·키링 설정 | 사진 등록은 선택이다. ‘사진이 있는 상대만 매칭’의 초기 기본값은 OFF다. 사용자가 키링 설정에서 켜면 사진 미등록 상대를 알고리즘 매칭에서 제외한다. 양쪽 설정을 각각 검사한다(2026-10-20 확정). |
| 변경 반영 시점 | 프로필·사진 옵션 변경은 저장 완료 즉시 새 매칭과 이미 받은 유효 제안에 적용한다. 제안 프로필은 최신 정보로 갱신하고, 변경된 대상 조건을 충족하지 못한 제안은 수락·채팅 전환을 막는다(2026-10-20 확정). |
| 나이 정보 | 가입은 만 19세 이상·상한 없음. 생년월일을 입력받고 한국 날짜(Asia/Seoul)와 생일 기준으로 계산한 만 나이만 공개한다. 희망 나이는 직접 지정한 범위 또는 ‘나이 상관없음’을 선택하며 양쪽 조건을 모두 충족해야 매칭한다(2026-10-20 확정). 생년월일 원본은 상대에게 반환하지 않는다. |
| 생활 정보 입력 | 흡연·음주는 필수, 종교는 선택으로 확정(2026-10-20). 흡연 4개·음주 6개·종교 6개 선택지를 사용한다. 필수 입력은 생활 불일치 시 매칭 제외를 뜻하지 않는다. |
| 닉네임·소개·사진 제한 | 닉네임 2~20자, 한글·영문·숫자·공백 허용 및 특수문자·이모지 금지. 자기소개는 선택·최대 200자·줄바꿈 최대 3개. 사진은 선택·1장·최대 10MB, JPG·PNG·WebP·HEIC 입력을 지원하는 것으로 확정(2026-10-20). |
| 목표 정책 | 흡연·음주·종교는 프로필에서 확인하고 사용자가 수락 여부를 판단한다. 최종 매칭 점수·제외 조건에는 사용하지 않는 방향이다. |
| 현재 개발 기준 | 첨부 v8 설문·결과 구조와 매칭 공식을 임시 기준으로 사용한다. v8에는 흡연·음주가 생활 점수에 포함되므로 목표 정책과 차이가 있다. 이번 초안이 그 차이를 해결하거나 계산 코드를 수정한 것은 아니다. |
| AI 기능 범위 | 실제 매칭 근거 설명, 상호 수락 후 시작 질문 제안, 위험 대화 감지·대응 지원. 모델·프롬프트·차단 기준은 후속 작업에서 검증한다. |

프로토타입에서 v8 점수를 쓸 때는 규칙 버전을 함께 기록한다. 흡연·음주를 점수에서 제외하기 전에는 해당 정보가 추천에 영향을 주지 않는다고 안내하지 않는다. 프로필과 설문에서 같은 정보를 받더라도 앱 공통 입력을 v8 응답으로 매핑하는 책임과 버전을 36·41·42번에서 맞추며, 서로 다른 두 값을 조용히 섞지 않는다.

출생연도만 받던 35번 초안을 생년월일 입력으로 바꾼다. 한국의 현재 날짜(Asia/Seoul)에서 생일 전후를 반영한 만 나이를 계산하고 표시와 매칭 조건에 같은 기준을 사용한다. 서버를 기준으로 계산 결과를 제공하는 구현안을 사용하며 실제 매칭 실행 위치와 전달 형식은 36·37번에서 맞춘다. 2월 29일생의 평년 나이 변경일과 실제 연령 확인 수단은 BE·PM 검토 항목이다. 생년월일 자기신고 입력은 본인·연령 인증을 뜻하지 않는다. 기존 birthYear만 있는 데이터의 월·일은 임의로 1월 1일로 채우지 않고 필요한 경우 본인에게 보완 입력을 받는다.

### 가입 연령과 희망 상대 나이

가입 허용 연령은 만 19세 이상이며 상한을 두지 않는다. 상한 없음은 존재하지 않는 날짜·미래 날짜를 허용한다는 뜻이 아니다. 희망 상대 나이는 첫 매칭 전에 직접 범위를 지정하거나 ‘나이 상관없음’을 선택해야 한다. 미선택을 상관없음으로 저장하거나 임의의 추천 범위를 자동 확정하지 않는다. 범위는 최소 만 19세부터 지정할 수 있고 최대값은 ‘상한 없음’을 선택할 수 있다. 상관없음도 가입 가능한 성인 사이에서만 적용한다.

스토어 연령 제한 설정과 별도 본인·연령 인증 방식은 앱 개발 이후 출시 준비 단계에서 결정한다(2026-10-20 사용자 결정). 이 결정은 현재 앱 골격 개발의 선행 조건이 아니다. 개발 중에는 입력받은 생년월일로 만 19세 미만 가입을 차단하는 기준을 유지하며, 자기신고 입력을 실제 연령 인증 완료로 표시하지 않는다. 스토어 설정·인증 연동은 아직 수행하지 않았다.

매칭은 `A의 희망 범위에 B의 현재 만 나이가 포함됨 AND B의 희망 범위에 A의 현재 만 나이가 포함됨`을 만족해야 한다. ANY는 해당 사용자의 희망 나이 제한을 해제한다. 범위의 최소·최대 나이는 모두 포함하며 같은 값으로 지정할 수 있다. 한쪽이라도 충족하지 않으면 성향 점수와 관계없이 제외한다. 나이 조건 통과가 최종 매칭을 보장하지는 않는다.

가입 시 나이를 영구 고정하지 않는다. 생일이 지나면 표시 나이와 새 매칭 판정에 갱신된 나이를 사용하고, 키링이 쓰는 나이·설정 데이터도 동기화한다. 갱신 기준 날짜·버전 전달과 오래된 데이터 또는 오프라인 상태의 처리 방식은 37번 계약에서 정한다. 생년월일 원본을 기기 간 방송할 필요는 없다. 기존 유효 제안에도 최신 나이·희망 조건을 적용하고, 수락 시 같은 기준으로 재검증한다.

| 희망 범위 30세~상한 없음 | 30세 이상 허용, 99세 상한을 추가하지 않음 |
| A는 27세·희망 25~32세, B는 30세·희망 28~35세 | 제외. B가 원하는 나이에 A가 포함되지 않음 |
| ‘나이 상관없음’ 명시 선택 / 미선택 | 각각 나이 선호 입력 완료 / 기본 조건 단계 미완료. 미성년자 허용으로 해석하지 않음 |

필드명·저장 코드는 API 계약 초안이다. RANGE에서 max의 null은 상한 없음이고, mode 미선택은 입력 미완료다. ANY의 min·max는 null로 정규화한다. 이 구분 없이 null을 일괄 미입력 또는 상관없음으로 해석하지 않는다.

‘공개 프로필 전체’에는 등록한 사진·닉네임·소개·표시 나이·성별·생활 정보를 포함한다. 생년월일 원본·소셜 ID·인증 토큰·키링 식별자·동의 기록·비공개 설문 원응답·상대 선호는 포함하지 않는다. 생년월일은 화면에서만 숨기는 것이 아니라 상대용 API 응답에서도 제외한다. AI 설명·시작 질문에 나이가 필요하면 공개된 나이만 전달한다. 종교는 미입력과 명시적 비공개를 저장 시 구분하되 상대에게는 모두 ‘종교 정보 비공개’로 표시한다. 미입력을 무교로 추정하지 않는다.

### 닉네임과 자기소개 검증

닉네임은 앞뒤 공백 제거 후 2~20자를 검사하고 내부 공백도 글자 수에 포함한다. 공백만으로 된 값은 허용하지 않는다. 한글·영문·숫자·공백의 허용 범위는 다음 구현 초안으로 FE·BE가 같은 검증기를 맞춘다: 한글 음절·자모, 영문 A~Z/a~z, 숫자 0~9, 일반 공백(U+0020). 줄바꿈·탭·보이지 않는 제어문자는 닉네임의 허용 공백으로 취급하지 않는다. 내부 연속 공백은 우선 그대로 보존하며 별도 합의 없이 합치거나 삭제하지 않는다.

닉네임 길이는 정규화 후 사용자가 보는 글자 단위로 센다. Unicode NFC 정규화 후 표시값과 중복 검사 키를 만들고, 영문 대소문자는 중복 검사에서만 무시하는 구현안을 사용한다. 예를 들어 `John Smith`와 `john smith`는 중복이다. 중복 조회와 최종 저장에 같은 규칙을 적용하고, 조회 후 다른 회원이 먼저 사용한 경우 저장 시 중복 오류를 반환한다. 기존 계정의 충돌은 임의로 이름을 변경하지 않고 별도 처리한다.

자기소개는 특수문자·이모지를 포함한 일반 텍스트로 표시하고 HTML로 실행하지 않는다. 사용자가 보는 글자 단위(확장 그래핌 클러스터)로 최대 200자를 계산한다. 줄바꿈은 LF로 통일해 글자 수에 포함하고 최대 3개까지 허용한다. 공백·줄바꿈만 있는 입력은 null로 처리한다. 앱 글자 수 표시와 서버 검증은 동일 기준을 사용한다.

| 검토 사례 | 기대 결과 |
| --- | --- |
| `John Smith`, `재준 106` | 허용 문자·길이 검사 통과. 중복 여부는 별도 확인 |
| ` John Smith ` | 앞뒤 공백 제거 후 `John Smith`로 검사·저장 |
| `J`, 공백뿐인 값, 21자 닉네임 | 길이 검사 실패 |
| `John_Smith`, `재준😊`, 탭·줄바꿈을 포함한 닉네임 | 허용 문자 검사 실패 |
| `John Smith`가 이미 있을 때 `john smith` | 중복 검사 실패 |
| 200자 자기소개 / 201자 자기소개 | 각각 통과 / 길이 초과 |
| 줄바꿈 3개 / 4개를 포함한 자기소개 | 각각 통과 / 줄바꿈 초과. 총 200자 제한도 함께 검사 |

### 프로필 사진 업로드와 등록 상태

사진 입력은 1장, 최대 10MB로 제한한다. API의 정확한 크기 단위는 10,000,000바이트 이하로 제안하며 FE·BE 계약에서 같은 값을 사용한다. JPG(JPEG)·PNG·WebP·HEIC 파일의 실제 형식과 디코딩 가능 여부를 서버에서 확인한다. 확장자만 바꾼 파일·손상 파일은 등록 완료로 처리하지 않는다.

앱에서 정사각형 자르기와 위치 조정을 제공한다. 서버는 방향 정보를 적용하고 자르기 결과·이미지 크기를 맞춘 뒤 위치정보 등 메타데이터를 제거하여 표시용 이미지를 저장한다. HEIC 등 입력은 JPEG 같은 공통 표시 형식으로 변환한다. 출력 픽셀 크기·압축 품질·최종 형식·픽셀 수 제한과 HEIC 지원 환경은 파일 API 계약 및 구현에서 정하고 검증한다. 업로드 원본의 장기 보관은 이번 정책에 포함하지 않는다.

| 상황 | 프로필 사진 상태·동작 |
| --- | --- |
| 처음 업로드 중 또는 실패 | 미등록. 기본 이미지 사용 |
| 업로드·서버 처리·프로필 연결 모두 완료 | 등록 완료. 이후 필요한 설정 버전 동기화 |
| 기존 사진 교체 중 또는 교체 실패 | 기존 사진과 등록 상태 유지 |
| 새 사진 교체 완료 | 새 이미지로 연결을 교체하고 기존 파일 정리 |
| 삭제 완료 | 기본 이미지·미등록 상태로 전환하고 키링 매칭에 쓰는 상태 갱신 |

사진 저장 요청만으로 `hasProfilePhoto=true`로 처리하지 않는다. 등록·삭제·교체의 최종 결과와 버전을 기준으로 37번 동기화 계약에 연결한다. 크기 초과·허용되지 않은 형식·디코딩/변환 실패·통신 실패는 원인을 구분해 재시도 또는 다른 파일 선택을 안내한다. 사진 필수 옵션에 의한 매칭 판정은 아래 규칙을 따른다.

### 흡연과 음주 및 종교 선택지

화면에서 어떤 답도 미리 선택하지 않는다. 흡연·음주는 하나씩 응답해야 프로필 단계를 완료할 수 있으며, 작성 도중 임시 저장은 허용한다. 종교는 건너뛸 수 있다. 흡연·음주에는 ‘모름’·‘공개하지 않음’·‘상관없음’을 추가하지 않는다. 필수 입력 검증은 프로필 완료 시 앱과 서버에 모두 적용한다.

아래 저장 코드는 계약 초안이며 화면 표시명과 분리한다. 표시 순서를 숫자 점수나 흡연·음주 정도의 순서로 해석하지 않는다.

| 흡연 | 비흡연 | NON_SMOKER |
| 흡연 | 전자담배 | E_CIGARETTE |

흡연은 종류와 상황, 음주는 상황과 빈도를 함께 묻는 자기소개용 분류다. 예를 들어 전자담배를 술자리에서만 피우거나 중요한 자리에서 월 1회 마시는 사람은 복수 선택지에 해당할 수 있다. 현재는 사용자가 자신을 가장 잘 설명하는 항목 하나를 고르는 UI 안내를 제안하며, 종류·상황별 우선순위나 병용자 규칙을 서버에서 임의 추론하지 않는다. ‘흡연’의 범위와 ‘중요한 자리’의 설명·음주 횟수 기준은 FE·PM 검토에서 보완한다.

새 프로필 응답은 기존 v8의 흡연 3단계·월 음주일수 4단계와 의미가 다르다. 전자담배를 매일 흡연으로, 주간 횟수를 월간 음주일수로 자동 환산하지 않는다. 프로필 선택지 버전을 따로 관리하고, 기존 v8 원응답이 있으면 그 버전과 함께 보존한다. 매핑 또는 해당 생활 항목 제외가 검토되기 전에는 새 프로필 응답으로 v8 응답을 덮어쓰지 않는다. 앱 골격은 새 프로필 선택지와 가상 매칭 결과로 연결할 수 있으며, 실제 계산 연동은 36·41·42번에서 버전·중복 질문·변환 불가 처리를 합의한 뒤 적용한다.

### 사진이 있는 상대만 매칭

설정 위치는 사용자 키링 설정이며 표시 이름은 ‘사진이 있는 상대만 매칭’으로 제안한다. ON이면 사진이 없는 상대와는 매칭하지 않고, OFF이면 본인 설정으로 상대 사진 유무를 제한하지 않는다. OFF여도 상대가 ON이면 상대의 조건을 충족해야 한다. 사진이 없는 사용자도 이 옵션을 켤 수 있으며, 본인 사진을 먼저 등록해야 켤 수 있다는 추가 제한은 두지 않는 초안이다.

초기 기본값은 OFF(false)로 확정한다. 설정을 처음 생성할 때 적용하고, 이후에는 사용자가 저장한 ON/OFF를 유지한다. 화면 재진입·재로그인·키링 재연결 때 기본값으로 덮어쓰지 않는다. 설정 조회 실패나 동기화 미완료를 신규 사용자 기본값과 혼동해 OFF로 간주하지 않으며, 해당 오류·대기 처리는 35·36·37번 계약에서 맞춘다. 기존 데이터에 필드가 없는 경우의 보완 방식은 계약 검토에서 정한다.

사진 미등록 시 안내 문구:

> 사진을 등록하지 않으면 ‘사진이 있는 상대만 매칭’을 켠 사용자와는 매칭되지 않아요.

설정 설명 문구:

> 켜면 프로필 사진을 등록한 상대만 매칭돼요.

판정은 `(A의 옵션이 OFF 또는 B의 사진 있음) 그리고 (B의 옵션이 OFF 또는 A의 사진 있음)`을 만족해야 통과한다. 미충족이면 성향 점수가 높아도 해당 쌍은 매칭하지 않는다. 사진 조건을 통과해도 성별·나이·성향·차단 등 나머지 조건을 통과해야 하므로 매칭을 보장하지 않는다. v8 점수 계산식 자체는 변경하지 않고 후보 자격 조건으로 분리한다.

| A 사진 | A 옵션 | B 사진 | B 옵션 | 사진 조건 결과 |
| --- | --- | --- | --- | --- |
| 없음 | OFF | 없음 | OFF | 통과. 사진 없는 두 사람을 일괄 제외하지 않음 |
| 있음 | ON | 없음 | OFF | 제외. A가 사진 있는 상대만 허용 |
| 없음 | OFF | 있음 | ON | 제외. B가 사진 있는 상대만 허용 |
| 없음 | ON | 있음 | OFF | 통과. A는 B 사진 조건 충족, B는 사진을 제한하지 않음 |
| 있음 | ON | 있음 | ON | 통과 |
| 없음 | ON | 없음 | ON | 제외 |

`hasProfilePhoto`는 등록 완료된 프로필 사진 존재 여부로 산출하는 필드 초안이다. 기본 아바타·업로드 중·실패 상태는 사진 등록으로 세지 않는다. 기기에 사진 원본을 전송할 필요는 없으며, 실제 계산 위치에 필요한 사진 존재 여부·옵션·설정 버전 전달 방식은 36·37번에서 정의한다. 사진 등록·삭제 또는 옵션 변경은 저장 완료 즉시 새 매칭과 기존 유효 제안에 적용하고, 키링에는 해당 값과 버전을 동기화한다. 모르는 사진 상태를 임의로 ‘있음’으로 처리하지 않는다. 오래된 기기 상태로 최신 조건을 우회하지 않도록 버전 확인·동기화·알림 허용 기준을 BE·AI·IOT 계약에서 정한다.

### 변경 사항의 즉시 적용

‘즉시’의 기준은 서버에 변경이 성공적으로 저장된 시점이다. 저장 실패·업로드 중인 임시값은 적용하지 않는다. 사진은 업로드·서버 처리·프로필 연결 또는 삭제가 완료된 시점을 기준으로 한다. 프로필의 공개 항목은 기존 유효 제안에서도 최신 값으로 보여주며, 사진 옵션·사진 등록 상태·희망 나이 등 대상 조건이 달라지면 양쪽 조건으로 제안을 다시 검사한다. 흡연·음주·종교의 프로필 수정만으로 새 제외 조건이나 v8 응답 자동 변환을 추가하지 않는다.

재검사 대상은 수락 대기(PENDING)와 한쪽만 수락한 상태(WAITING_FOR_OTHER)다. 조건 미충족 제안은 양쪽 모두 더 이상 수락하거나 채팅방으로 전환할 수 없다. 이미 열린 화면이나 이전 알림으로 들어와도 최신 유효성을 확인한다. 조건을 계속 충족하는 제안은 최신 프로필을 표시한다. 구현 초안으로 조건 미충족 상태를 INVALIDATED로 구분하며, 사용자 거절과 구분해 ‘조건이 변경되어 종료된 제안이에요.’를 안내한다. 정확한 상태·오류 코드·이력 표시·프로필 접근 종료 처리는 38번 계약에서 정한다.

수락 요청 및 최종 상호 수락 처리에서도 최신 양쪽 조건을 다시 검증한다. 프로필 저장과 수락이 동시에 발생할 때 이전 버전으로 채팅이 열리지 않도록 처리 순서와 원자성을 35·38·43번에서 정의한다. 종료된 제안의 자동 복구·재생성, 조건을 계속 충족하는 상태에서 프로필 변경 전 수락을 재확인할지 여부는 별도 검토 항목이다. 이미 상호 수락해 열린 채팅방의 종료는 이번 즉시 적용 결정에 포함하지 않는다.

연결된 앱 화면은 변경 통지 또는 재조회로 갱신하며, 화면 갱신이 늦어도 서버의 수락 검증은 최신 조건을 적용한다. 오프라인 기기에 즉시 전달되는 것을 보장할 수는 없다. 키링에서 최신 상태를 확인할 수 없는 동안 매칭·알림을 어떻게 보류하고 재연결 시 복구할지는 36·37번에서 정한다. 즉시 적용 요건을 충족하려면 오프라인 독립 매칭 범위도 함께 조정해야 한다.

| 검토 사례 | 기대 결과 |
| --- | --- |
| 사진 없는 B의 제안을 받은 A가 사진 옵션을 OFF→ON으로 저장 | 기존 제안도 조건 미충족 처리, 양쪽 수락·채팅 전환 차단 |
| A의 옵션은 ON, B가 등록 사진 삭제 완료 | 새 매칭 제외 및 기존 대기·한쪽 수락 제안도 조건 미충족 처리 |
| 사진 교체 업로드 실패 | 기존 사진·등록 상태 유지. 실패한 임시값으로 제안 종료하지 않음 |
| B가 자기소개 변경 완료, 대상 조건은 계속 충족 | 기존 유효 제안에 최신 자기소개 표시. 새 제외 조건을 만들지 않음 |
| 조건 변경 전 열린 화면에서 늦게 수락 요청 | 최신 양쪽 조건 재검증, 미충족이면 수락 거절 |

## 3. 미입력과 응답 의미

| 값 | 의미 | 처리 초안 |
| --- | --- | --- |
| 미입력 / null | 일반적으로 아직 입력하지 않음. 필드별 명시적 의미는 예외 | 필수 프로필·기본 조건은 단계 미완료. 선택 프로필은 완료 가능. 설문은 미응답 상태로 보존. 희망 나이 max의 null(상한 없음)과 ANY 모드의 경계값 null은 위 계약대로 구분 |
| UNKNOWN / 모름 | 질문에는 응답했지만 판단할 수 없음 | v8 설문에서 지원하는 문항에 한해 사용. 새 흡연·음주·종교 프로필 선택지에는 없음. 중간값·0점·불일치로 바꾸지 않음 |
| UNDISCLOSED / 응답하지 않음 | 해당 프로필 정보를 공개하지 않겠음 | 종교에서 허용, 값 추정 금지. 필수 흡연·음주에는 허용하지 않음 |
| ANY / 상관없음 | 상대 조건에 제한을 두지 않음 | 본인 특성으로 저장하지 않음. 설문은 v8의 ANY 처리를 유지. 새 성별·나이 기본 조건의 제한 없음과 구분해 매핑 |
| NONE / 없음 | 실제로 종교가 없거나 음주하지 않음 등 명확한 답변 | UNKNOWN·null과 구분하여 저장 |

v8는 생활 선호를 ‘상관없음’으로 답해도 일부 항목의 기본 유사도가 남을 수 있다. 현 계산을 유지하는 동안 이를 ‘점수에서 완전히 제외됨’으로 설명하지 않는다. 설문 화면 완료와 점수 산출 가능 여부도 구분한다. 모두 답했어도 유효 응답 부족이면 보완할 영역을 안내한다.

## 4. 화면 진입과 재개

아래 상태 이름은 공통 계약 검토용이며 이미 구현된 API가 아니다. 로그인·회원가입 완료와 매칭 준비 완료를 별도 관리한다. 현재 인증 명세의 signupCompleted 하나로 다음 화면을 결정하면 키링·설문 단계가 생략될 수 있다.

| 상태 초안 | 진입 조건·다음 행동 | 실패·재개 |
| --- | --- | --- |
| LOGIN_REQUIRED | 유효한 서비스 인증 없음. 소셜 로그인 진행 | 취소·인증 실패·연결 오류를 구분하고 재시도 |
| KEYRING_REQUIRED | 인증됨, 등록한 키링 없음. 등록 또는 구매 안내 | 등록 검증 실패 시 같은 단계 유지. 결제 성공으로 우회 금지 |
| PROFILE_REQUIRED | 키링 등록 완료, 필수 프로필·필수 동의 미완료 | 저장된 입력을 복원하고 미완료 항목부터 재개 |
| SURVEY_REQUIRED | 프로필 완료, 설문 미완료 또는 계산 가능한 결과 없음 | 마지막 저장 문항부터 재개. 유효 응답 부족 영역을 보완 |
| PREFERENCES_REQUIRED | 성향 결과 있음, 희망 성별·나이 미설정 | 나이는 범위 또는 상관없음을 직접 선택해야 완료. 미선택 자동 확정 금지. 잘못된 범위는 필드 오류로 표시하고 보존 |
| SYNC_PENDING | 가입 입력 완료, 필요한 설정·규칙 버전의 반영 미확인 | 홈·내 설정에서 대기·실패·재시도 표시. 신규 매칭 시작은 보류 |
| READY | 등록·필수 입력·산출·기본 조건·필요한 동기화가 모두 충족 | 매칭 ON/OFF와 연결 상태를 별도로 표시 |

서버 저장 성공과 키링 반영 성공을 구분하고, 설정 전송만으로 반영 완료 처리하지 않는다. 어떤 데이터를 키링에 저장할지와 완료 응답은 37번에서 결정한다. 첫 개발은 가상 완료 응답으로 연결하되 실기기 검증으로 표시하지 않는다.

가을의 35번 인증 계약과 함께 조정할 부분:

- signupCompleted의 의미는 기존 기본 회원가입 완료로 유지할 수 있으나, FE는 별도 단계 조회 결과로 이동한다. 정확한 응답 필드·조회 API는 BE·FE가 결정한다.
- 키링을 프로필보다 먼저 등록하려면 가입 미완료 회원도 키링 등록·등록 상태 조회 등 필요한 API에 접근할 수 있어야 한다. 현재 SIGNUP_REQUIRED 예외 목록을 검토한다.
- ALREADY_SIGNED_UP은 재시도 성공으로 취급하되 무조건 홈으로 이동하지 않고 다음 미완료 단계를 조회한다.
- 닉네임의 공개 시점은 상호 수락 이후에서 유효 제안 조회 시점으로 수정한다.
- 닉네임을 2~20자 및 내부 공백 허용으로 바꾸고 중복 조회·최종 저장·FE 글자 수 표시의 정규화 기준을 맞춘다. 기존 2~10자·공백 금지 검증을 그대로 유지하지 않는다.
- birthYear를 birthDate로 바꾸고 날짜 검증·나이 계산·공개 프로필의 age 응답을 맞춘다. 생일 전후·미래 날짜·존재하지 않는 날짜·상대 응답 원본 미노출 사례를 검증한다.
- 앱 라우팅뿐 아니라 서버에서도 해당 단계의 접근 조건을 확인한다.

## 5. 매칭 제안과 채팅

유효한 제안의 당사자만 상대 공개 프로필과 매칭 근거를 조회할 수 있다. 임의 회원 ID를 넣어 다른 회원의 프로필을 조회할 수 있는 권한으로 확대하지 않는다.

| 제안 상태 초안 | 프로필·채팅 동작 |
| --- | --- |
| PENDING | 양쪽 모두 상대 공개 프로필을 보고 수락·거절 가능. 채팅 불가 |
| WAITING_FOR_OTHER | 한쪽만 수락. 유효 기간 동안 프로필 확인, 상대 응답 대기. 채팅 불가 |
| ACCEPTED | 양쪽 수락. 동일 상대의 활성 채팅방 하나로 연결하고 시작 질문 표시 |
| INVALIDATED | 변경된 대상 조건 미충족으로 종료된 제안. 양쪽 수락·새 채팅 생성 금지. 상태명은 초안이며 거절·만료와 구분 |
| REJECTED / EXPIRED | 새 채팅 생성 금지. 프로필 조회 종료 시점과 FE 캐시 정리 방식은 38번에서 명시 |

기존 Jira의 기회 유지 7일·제안 생성 후 24시간·거절 후 30일 제한·퇴장한 상대와 재매칭 금지·서로 다른 상대와 여러 채팅 허용은 이번 변경에서 재설계하지 않는다. 정확한 시간 경계·동시 요청·기존 채팅방 재사용은 38·43번에서 정의한다. 프로필 공개 시점 변경이 채팅 권한을 앞당기지 않는다.

매칭 실행 위치(앱·서버·키링), 오프라인 계산 가능 범위, 키링 알림 발생 조건은 아직 파트 합의가 필요하다. 매칭 이벤트에는 판단 당시 규칙·성향 결과 버전과 설명 근거를 연결하는 방식을 36·37·38번에서 정한다. 나중에 프로필이 바뀌어도 다른 근거로 과거 알림을 설명하지 않도록 한다.

## 6. 화면 연결용 예시

예시는 데이터 형태와 기대 동작을 설명하며 HTTP 엔드포인트·최종 오류 코드 확정이 아니다. 실제 요청·응답은 각 담당자의 API 명세에서 관리한다. 식별자는 가상 값이다.

정상: 인증·키링 등록·프로필 저장을 마쳤지만 설문이 미완료인 경우.

```json
{
  "userId": 1024,
  "signupCompleted": true,
  "nextStep": "SURVEY_REQUIRED",
  "onboardingCompleted": false,
  "matchingReady": false,
  "survey": { "version": "v8", "answeredCount": 12, "questionCount": 80, "calculable": false },
  "keyring": { "registered": true, "syncState": "PENDING" }
}
```

검증 오류: 나이 범위의 순서가 잘못된 경우.

```json
{
  "code": "INVALID_AGE_RANGE",
  "message": "최소 나이는 최대 나이보다 클 수 없습니다.",
  "fields": ["desiredAgeMin", "desiredAgeMax"]
}
```

권한·진입 오류: 등록하지 않은 상태로 프로필 단계에 접근한 경우.

```json
{
  "code": "KEYRING_REQUIRED",
  "message": "키링 등록을 완료해 주세요.",
  "nextStep": "KEYRING_REQUIRED"
}
```

## 7. AI 기능의 개발 경계

| 기능 | 입력·출력 초안 | 최소 검증·실패 시 동작 |
| --- | --- | --- |
| 매칭 이유 설명 | 실제 매칭 판정의 근거·규칙 버전 → 근거에 대응하는 짧은 설명 | 근거 없는 설명·점수를 성공 확률로 표현하는 출력 금지. 생성 실패 시 확인된 규칙 문장 사용. 설명 생성 실패로 매칭 자체를 취소하지 않음 |
| 아이스브레이킹 | 상호 수락한 두 사람의 공개 정보 → 시작 질문 3개 | 선택·수정 후 사용자 직접 전송. 부족한 정보는 일반 질문으로 대체. 비공개 응답·민감한 생활 정보를 소재로 추정하지 않음. 실패해도 채팅 가능 |
| 위험 대화 감지 | 분석 대상으로 합의한 메시지·필요한 문맥 → 위험 유형·판정 결과 | 정상 금전 대화·인용·은어를 포함한 한국어 사례로 오탐·누락·응답 시간 확인. 판정과 경고·차단·계정 제재 정책 분리 |

각 기능의 API 형식, 실패 상태, 모델·프롬프트 버전과 검증 사례를 성현이 작성하고 영빈(BE)·재준 또는 순철(FE)과 맞춘다. Jira 작업은 [46번 매칭 이유](https://ssafy.atlassian.net/browse/S15P31E106-46), [47번 시작 질문](https://ssafy.atlassian.net/browse/S15P31E106-47), [48번 위험 대화](https://ssafy.atlassian.net/browse/S15P31E106-48)로 분리한다. 이 세 작업은 첫 계약 작성 범위이며 실제 기능 구현은 후속 Story로 연결한다. 위험 감지 서비스 장애 시 메시지 전달 정책, 분석 안내·외부 전송 범위·보관 범위는 적용 전에 PM·BE·AI가 결정한다. AI가 없더라도 기본 신고·차단은 별도 제공한다.

개인 성향 산출·16유형 분류는 이미 영빈이 진행 중인 41·42번을 유지한다. 성현의 36번은 그 결과를 받아 두 사람의 매칭을 비교하고 IOT·BE와 연결하는 계약·검증을 담당한다. 새 AI 기능은 별도 Story로 관리한다.

## 9. 호환성과 적용 순서

1. 34번 초안을 검토하고 기존 Jira의 생활 필수 조건·수락 전 프로필 비공개 지시를 갱신한다.
2. 35·45번에서 가입 단계와 키링 등록 권한을 맞추고, 38·43번에서 제안 당사자에게 공개 프로필을 반환하도록 계약·검증을 조정한다.
3. 41·42번의 설문·성향 데이터와 36·37번의 매칭·키링 계약을 맞춘다. 가상 데이터로 FE 흐름을 먼저 연결한다.
4. AI 기능의 입출력을 합의하고 예시 응답을 실제 기능으로 교체한다.
5. 후속으로 v8 계산을 변경할 때 규칙 버전을 올리고 원응답 재계산·키링 동기화·설명 근거의 호환성을 검증한다.

이 문서는 기존 전송 형식과 호환되는 변경이라고 보장하지 않는다. 특히 단계 응답 추가·프로필 공개 시점 변경·birthYear에서 birthDate로의 전환은 FE·BE 동시 조정이 필요하다. 생년월일 변경은 35번 계약 갱신 → 45번 저장·검증·나이 계산 구현 → FE 입력·공개 응답 연동 순서로 조율한다. 검토 전 가을의 작업 브랜치를 직접 수정하지 않는다. 실제 API·펌웨어 형식은 담당 명세를 단일 기준으로 유지한다.

기존 19~99 개발 초안은 폐기한다. 새 계약은 나이 선택 모드와 상한 없음을 표현해야 하며, 기존 max=99를 사용자 확인 없이 무제한으로 변환하지 않는다. 프로필 표시·가입 검증·양방향 매칭·키링 동기화에 동일한 한국 날짜와 나이 기준을 적용한다. 계약 검토 후 서버 검증과 FE 선택 UI를 함께 반영하고, 생일 경계·같은 최소/최대·상한 없음·미선택·양방향 불일치 사례를 확인한다.

사진 옵션은 신규 설정 생성 시 false로 초기화하는 계약을 맞춘 뒤 FE 초기 표시와 키링 동기화에 반영한다. 기존 저장값은 보존한다. 최초 OFF, 사용자가 ON 저장 후 재진입, 상대만 ON인 양방향 제외 사례를 검증한다. 필드명과 실제 전송 형식은 담당 계약에서 확정한다.

즉시 적용은 35번 저장·버전 계약과 36번 양방향 검사 → 38번 제안 재검증·종료 계약 → 43번 수락의 동시성 처리 및 FE 갱신 → 37번 키링 최신 상태 확인·동기화 순으로 맞춘다. 이미 발송한 알림이나 내려받은 화면을 회수했다고 가정하지 않고 진입·수락 시 최신 상태를 검증한다. 기존 제안 상태에 종료 사유가 추가될 수 있으므로 FE·BE가 함께 반영한다.
