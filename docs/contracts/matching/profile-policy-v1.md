# 가입과 매칭의 앱 개발 기준

| 항목 | 내용 |
| --- | --- |
| 버전·변경일 | v0.1.0-draft / 2026-10-19 |
| 담당 | 이재준(PM·FE) |
| 관련 Story | S15P31E106-34 |
| 영향 파트 | FE·BE·AI·IOT |
| 검토 대상 | 황순철(FE), 가을·김영빈(BE), 황성현(AI), 김종무(IOT) |
| 상태 | 개발용 초안. 파트 검토·승인과 MR 병합 전이며 정책 확정·구현 완료를 뜻하지 않는다. |

이 문서는 앱의 가입부터 매칭 제안과 채팅 진입까지 연결하기 위한 기준이다. 사용자가 결정한 흐름을 우선 반영하고, 입력값과 상태 이름은 검토 가능한 초안으로 제시한다. 지금은 앱의 틀을 먼저 만들며 문항·가중치·추천 기준 개선은 후속으로 분리한다.

## 1. 결정 사항과 임시 사용 범위

| 구분 | 기준 |
| --- | --- |
| 확정된 흐름 | 구글·카카오·네이버 로그인 → 키링 등록 → 본인 프로필 → 성향테스트 → 희망 성별·나이 설정 → 준비 상태 확인 → 서비스 이용 |
| 키링 등록 | 등록한 회원만 프로필 이후 단계로 진행한다. 미보유자는 구매 링크를 제공하되 구매 링크 방문·결제만으로 등록 완료 처리하지 않는다. 등록 실패는 재시도 경로를 제공한다. |
| 매칭 방향 | 성향테스트를 바탕으로 매칭하고 희망 성별·나이는 별도 기본 조건으로 설정한다. 생활 조건 하나가 다르다는 이유로 무조건 제외하는 기존 설계는 사용하지 않는다. |
| 프로필과 채팅 | 유효한 매칭 제안의 당사자는 수락·거절 전에 상대의 공개 프로필 전체를 확인한다. 채팅 입장·메시지 전송은 상호 수락 이후에만 허용한다. |
| 목표 정책 | 흡연·음주·종교는 프로필에서 확인하고 사용자가 수락 여부를 판단한다. 최종 매칭 점수·제외 조건에는 사용하지 않는 방향이다. |
| 현재 개발 기준 | 첨부 v8 설문·결과 구조와 매칭 공식을 임시 기준으로 사용한다. v8에는 흡연·음주가 생활 점수에 포함되므로 목표 정책과 차이가 있다. 이번 초안이 그 차이를 해결하거나 계산 코드를 수정한 것은 아니다. |
| AI 기능 범위 | 실제 매칭 근거 설명, 상호 수락 후 시작 질문 제안, 위험 대화 감지·대응 지원. 모델·프롬프트·차단 기준은 후속 작업에서 검증한다. |

프로토타입에서 v8 점수를 쓸 때는 규칙 버전을 함께 기록한다. 흡연·음주를 점수에서 제외하기 전에는 해당 정보가 추천에 영향을 주지 않는다고 안내하지 않는다. 프로필과 설문에서 같은 정보를 받더라도 앱 공통 입력을 v8 응답으로 매핑하는 책임과 버전을 36·41·42번에서 맞추며, 서로 다른 두 값을 조용히 섞지 않는다.

## 2. 입력 항목 초안

아래 필수 여부·길이·선택지·자료형은 화면과 데이터 모델을 만드는 개발 초안이다. 기존 인증 명세의 입력값을 가능한 한 유지했으며 파트 검토 전 최종 정책으로 안내하지 않는다. 가입 단계의 약관 동의는 인증 계약과 연결하며 별도의 이상형 입력 단계로 취급하지 않는다.

| 필드 | 자료형·입력 방식 | 초안 필수 여부·허용 범위 | 사용·공개 |
| --- | --- | --- | --- |
| provider / providerSubject | 서버가 검증한 소셜 종류·고유 ID | google / kakao / naver와 소셜 고유 ID. 앱의 임의 자기신고값으로 인증하지 않는다. | 계정 식별 전용, 상대 미공개. 현 35번 명세는 이메일·이름·사진을 소셜에서 수집하지 않는다. |
| nickname | string / 텍스트 | 필수. 35번 초안의 2~10자 한글·영문·숫자, 앞뒤 공백 제거, 대소문자 무시 중복 검사와 정합성 유지 | 제안 시 공개, 점수 미사용 |
| gender | string / 단일 선택 | 필수. 35번 초안의 MALE / FEMALE을 임시 사용. 선택지 확장은 후속 검토 | 기본 성별 조건, 제안 시 공개 |
| birthYear | integer / 연도 선택 | 필수. 개발 화면 초안은 현재 연도-99부터 현재 연도-19까지. 실제 서비스의 최소·최대 연령과 확인 수단은 PM 결정 전 미확정 | 기본 나이 조건, 제안에는 계산한 나이만 표시 |
| profileImageId | string 또는 null / 업로드 | 선택. 미입력은 기본 이미지. 장수·형식·크기·업로드 검증은 파일 API에서 결정 | 등록된 사진은 제안 시 공개, 점수 미사용 |
| introduction | string 또는 null / 텍스트 | 선택. 초안 1~200자, 공백뿐인 입력은 null로 정규화 | 제안 시 공개, 점수 미사용 |
| smokingStatus | string 또는 null / 단일 선택 | 선택. NON_SMOKER / NON_DAILY / DAILY / UNKNOWN / UNDISCLOSED | 목표는 프로필 전용. v8 임시 계산에서는 Q55·Q76의 영향이 남음 |
| drinkingFrequency | string 또는 null / 단일 선택 | 선택. 최근 3개월 기준 월 음주일수 NONE / DAYS_1_3 / DAYS_4_7 / DAYS_8_PLUS / UNKNOWN / UNDISCLOSED | 음주 여부는 NONE과 구분해 표시. v8 임시 계산에서는 Q56·Q77의 영향이 남음 |
| religion | string 또는 null / 단일 선택 | 선택. NONE / PROTESTANT / CATHOLIC / BUDDHIST / OTHER / UNKNOWN / UNDISCLOSED. 선택지는 검토용 초안 | 제안 시 공개, v8 계산에 없음 |
| desiredGenders | string[] / 복수 선택 | 기본 조건 단계 필수. gender와 같은 선택지 중 1개 이상. 모두 선택하면 성별 제한 없음 | 양쪽 조건 비교, 상대 미공개 |
| desiredAgeMin / desiredAgeMax | integer / 범위 선택 | 필수. 개발 초안 19~99, min ≤ max. 나이 산식과 범위는 birthYear 기준과 함께 확정 | 양쪽 조건 비교, 상대 미공개 |
| surveyVersion / answers | string / 문항 ID별 응답 | 임시 기준은 v8 80문항. 문항별 타입·복수 선택 제한은 41번, 점수 산출 가능 여부는 42번이 정의 | 36번 매칭 입력으로 전달. 설문 원응답은 상대 미공개 |
| agreement records | 서버 저장 동의 항목·버전·시각 | 35번 약관 API 기준. 사용자가 보지 않은 버전에 동의한 것으로 기록하지 않음 | 상대 미공개 |

출생연도만으로는 생일에 따른 만 나이를 정확히 산출할 수 없다. 35번 초안의 연 나이 계산을 실제 만 나이 확인 완료로 표시하지 않는다. 생년월일 수집 여부·연령 확인 수단·상대 나이 범위 산식은 같은 결정으로 묶어 검토한다. 확인 전 실제 서비스의 연령 검증 완료를 주장하지 않는다.

‘공개 프로필 전체’에는 등록한 사진·닉네임·소개·표시 나이·성별·생활 정보를 포함한다. 소셜 ID·인증 토큰·키링 식별자·동의 기록·비공개 설문 원응답·상대 선호는 포함하지 않는다. 미입력은 ‘미입력’, UNDISCLOSED는 ‘공개하지 않음’으로 표시하며 값을 추정하지 않는다.

## 3. 미입력과 응답 의미

| 값 | 의미 | 처리 초안 |
| --- | --- | --- |
| 미입력 / null | 아직 입력하지 않음 | 필수 프로필·기본 조건은 단계 미완료. 선택 프로필은 완료 가능. 설문은 미응답 상태로 보존 |
| UNKNOWN / 모름 | 질문에는 응답했지만 판단할 수 없음 | 중간값·0점·불일치로 바꾸지 않음. v8 문항별 산출 규칙에 따라 유효 응답에서 제외 |
| UNDISCLOSED / 응답하지 않음 | 해당 프로필 정보를 공개하지 않겠음 | 선택 프로필에서 허용, 값 추정 금지. v8에 변환할 때 미측정 매핑을 명시 |
| ANY / 상관없음 | 상대 조건에 제한을 두지 않음 | 본인 특성으로 저장하지 않음. 설문은 v8의 ANY 처리를 유지. 새 성별·나이 기본 조건의 제한 없음과 구분해 매핑 |
| NONE / 없음 | 실제로 종교가 없거나 음주하지 않음 등 명확한 답변 | UNKNOWN·null과 구분하여 저장 |

v8는 생활 선호를 ‘상관없음’으로 답해도 일부 항목의 기본 유사도가 남을 수 있다. 현 계산을 유지하는 동안 이를 ‘점수에서 완전히 제외됨’으로 설명하지 않는다. 설문 화면 완료와 점수 산출 가능 여부도 구분한다. 모두 답했어도 유효 응답 부족이면 보완할 영역을 안내한다.

## 4. 화면 진입과 재개

아래 상태 이름은 공통 계약 검토용이며 이미 구현된 API가 아니다. 로그인·회원가입 완료와 매칭 준비 완료를 별도 관리한다. 현재 인증 명세의 signupCompleted 하나로 다음 화면을 결정하면 키링·설문 단계가 생략될 수 있다.

| 상태 초안 | 진입 조건·다음 행동 | 실패·재개 |
| --- | --- | --- |
| LOGIN_REQUIRED | 유효한 서비스 인증 없음. 소셜 로그인 진행 | 취소·인증 실패·연결 오류를 구분하고 재시도 |
| KEYRING_REQUIRED | 인증됨, 등록한 키링 없음. 등록 또는 구매 안내 | 등록 검증 실패 시 같은 단계 유지. 결제 성공으로 우회 금지 |
| PROFILE_REQUIRED | 키링 등록 완료, 필수 프로필·필수 동의 미완료 | 저장된 입력을 복원하고 미완료 항목부터 재개 |
| SURVEY_REQUIRED | 프로필 완료, 설문 미완료 또는 계산 가능한 결과 없음 | 마지막 저장 문항부터 재개. 유효 응답 부족 영역을 보완 |
| PREFERENCES_REQUIRED | 성향 결과 있음, 희망 성별·나이 미설정 | 잘못된 범위는 필드 오류로 표시하고 보존 |
| SYNC_PENDING | 가입 입력 완료, 필요한 설정·규칙 버전의 반영 미확인 | 홈·내 설정에서 대기·실패·재시도 표시. 신규 매칭 시작은 보류 |
| READY | 등록·필수 입력·산출·기본 조건·필요한 동기화가 모두 충족 | 매칭 ON/OFF와 연결 상태를 별도로 표시 |

서버 저장 성공과 키링 반영 성공을 구분하고, 설정 전송만으로 반영 완료 처리하지 않는다. 어떤 데이터를 키링에 저장할지와 완료 응답은 37번에서 결정한다. 첫 개발은 가상 완료 응답으로 연결하되 실기기 검증으로 표시하지 않는다.

가을의 35번 인증 계약과 함께 조정할 부분:

- signupCompleted의 의미는 기존 기본 회원가입 완료로 유지할 수 있으나, FE는 별도 단계 조회 결과로 이동한다. 정확한 응답 필드·조회 API는 BE·FE가 결정한다.
- 키링을 프로필보다 먼저 등록하려면 가입 미완료 회원도 키링 등록·등록 상태 조회 등 필요한 API에 접근할 수 있어야 한다. 현재 SIGNUP_REQUIRED 예외 목록을 검토한다.
- ALREADY_SIGNED_UP은 재시도 성공으로 취급하되 무조건 홈으로 이동하지 않고 다음 미완료 단계를 조회한다.
- 닉네임의 공개 시점은 상호 수락 이후에서 유효 제안 조회 시점으로 수정한다.
- 앱 라우팅뿐 아니라 서버에서도 해당 단계의 접근 조건을 확인한다.

## 5. 매칭 제안과 채팅

유효한 제안의 당사자만 상대 공개 프로필과 매칭 근거를 조회할 수 있다. 임의 회원 ID를 넣어 다른 회원의 프로필을 조회할 수 있는 권한으로 확대하지 않는다.

| 제안 상태 초안 | 프로필·채팅 동작 |
| --- | --- |
| PENDING | 양쪽 모두 상대 공개 프로필을 보고 수락·거절 가능. 채팅 불가 |
| WAITING_FOR_OTHER | 한쪽만 수락. 유효 기간 동안 프로필 확인, 상대 응답 대기. 채팅 불가 |
| ACCEPTED | 양쪽 수락. 동일 상대의 활성 채팅방 하나로 연결하고 시작 질문 표시 |
| REJECTED / EXPIRED | 새 채팅 생성 금지. 프로필 조회 종료 시점과 FE 캐시 정리 방식은 38번에서 명시 |

기존 Jira의 기회 유지 7일·제안 생성 후 24시간·거절 후 30일 제한·퇴장한 상대와 재매칭 금지·서로 다른 상대와 여러 채팅 허용은 이번 변경에서 재설계하지 않는다. 정확한 시간 경계·동시 요청·기존 채팅방 재사용은 38·43번에서 정의한다. 프로필 공개 시점 변경이 채팅 권한을 앞당기지 않는다.

매칭 실행 위치(앱·서버·키링), 오프라인 계산 가능 범위, 키링 알림 발생 조건은 아직 파트 합의가 필요하다. 매칭 이벤트에는 판단 당시 규칙·성향 결과 버전과 설명 근거를 연결하는 방식을 36·37·38번에서 정한다. 나중에 프로필이 바뀌어도 다른 근거로 과거 알림을 설명하지 않도록 한다.

## 6. 화면 연결용 예시

예시는 데이터 형태와 기대 동작을 설명하며 HTTP 엔드포인트·최종 오류 코드 확정이 아니다. 실제 요청·응답은 각 담당자의 API 명세에서 관리한다. 식별자는 가상 값이다.

정상: 인증·키링 등록·프로필 저장을 마쳤지만 설문이 미완료인 경우.

```json
{
  "userId": 1024,
  "signupCompleted": true,
  "nextStep": "SURVEY_REQUIRED",
  "onboardingCompleted": false,
  "matchingReady": false,
  "survey": { "version": "v8", "answeredCount": 12, "questionCount": 80, "calculable": false },
  "keyring": { "registered": true, "syncState": "PENDING" }
}
```

검증 오류: 나이 범위의 순서가 잘못된 경우.

```json
{
  "code": "INVALID_AGE_RANGE",
  "message": "최소 나이는 최대 나이보다 클 수 없습니다.",
  "fields": ["desiredAgeMin", "desiredAgeMax"]
}
```

권한·진입 오류: 등록하지 않은 상태로 프로필 단계에 접근한 경우.

```json
{
  "code": "KEYRING_REQUIRED",
  "message": "키링 등록을 완료해 주세요.",
  "nextStep": "KEYRING_REQUIRED"
}
```

## 7. AI 기능의 개발 경계

| 기능 | 입력·출력 초안 | 최소 검증·실패 시 동작 |
| --- | --- | --- |
| 매칭 이유 설명 | 실제 매칭 판정의 근거·규칙 버전 → 근거에 대응하는 짧은 설명 | 근거 없는 설명·점수를 성공 확률로 표현하는 출력 금지. 생성 실패 시 확인된 규칙 문장 사용. 설명 생성 실패로 매칭 자체를 취소하지 않음 |
| 아이스브레이킹 | 상호 수락한 두 사람의 공개 정보 → 시작 질문 3개 | 선택·수정 후 사용자 직접 전송. 부족한 정보는 일반 질문으로 대체. 비공개 응답·민감한 생활 정보를 소재로 추정하지 않음. 실패해도 채팅 가능 |
| 위험 대화 감지 | 분석 대상으로 합의한 메시지·필요한 문맥 → 위험 유형·판정 결과 | 정상 금전 대화·인용·은어를 포함한 한국어 사례로 오탐·누락·응답 시간 확인. 판정과 경고·차단·계정 제재 정책 분리 |

각 기능의 API 형식, 실패 상태, 모델·프롬프트 버전과 검증 사례를 성현이 작성하고 영빈(BE)·재준 또는 순철(FE)과 맞춘다. Jira 작업은 [46번 매칭 이유](https://ssafy.atlassian.net/browse/S15P31E106-46), [47번 시작 질문](https://ssafy.atlassian.net/browse/S15P31E106-47), [48번 위험 대화](https://ssafy.atlassian.net/browse/S15P31E106-48)로 분리한다. 이 세 작업은 첫 계약 작성 범위이며 실제 기능 구현은 후속 Story로 연결한다. 위험 감지 서비스 장애 시 메시지 전달 정책, 분석 안내·외부 전송 범위·보관 범위는 적용 전에 PM·BE·AI가 결정한다. AI가 없더라도 기본 신고·차단은 별도 제공한다.

개인 성향 산출·16유형 분류는 이미 영빈이 진행 중인 41·42번을 유지한다. 성현의 36번은 그 결과를 받아 두 사람의 매칭을 비교하고 IOT·BE와 연결하는 계약·검증을 담당한다. 새 AI 기능은 별도 Story로 관리한다.

## 9. 호환성과 적용 순서

1. 34번 초안을 검토하고 기존 Jira의 생활 필수 조건·수락 전 프로필 비공개 지시를 갱신한다.
2. 35·45번에서 가입 단계와 키링 등록 권한을 맞추고, 38·43번에서 제안 당사자에게 공개 프로필을 반환하도록 계약·검증을 조정한다.
3. 41·42번의 설문·성향 데이터와 36·37번의 매칭·키링 계약을 맞춘다. 가상 데이터로 FE 흐름을 먼저 연결한다.
4. AI 기능의 입출력을 합의하고 예시 응답을 실제 기능으로 교체한다.
5. 후속으로 v8 계산을 변경할 때 규칙 버전을 올리고 원응답 재계산·키링 동기화·설명 근거의 호환성을 검증한다.

이 문서는 기존 전송 형식과 호환되는 변경이라고 보장하지 않는다. 특히 단계 응답 추가와 프로필 공개 시점 변경은 FE·BE 동시 조정이 필요하다. 검토 전 가을의 작업 브랜치를 직접 수정하지 않는다. 실제 API·펌웨어 형식은 담당 명세를 단일 기준으로 유지한다.
