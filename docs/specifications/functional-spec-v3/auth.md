### AUTH-01 소셜 로그인

**압축 MVP CM13 변경(2026-10-26 사용자 재확정):** 로그인은 구글·카카오·네이버 3종을 모두 제공한다. 직전의 네이버 후속 결정을 대체한다. 앱 선택 화면과 서버 인증 허용 제공자를 3종으로 맞추고 각 제공자의 정상·취소·실패·재로그인을 검증한다. 제공자/고유 식별값 기반 계정 연결, 서로 다른 소셜 계정 자동 통합 금지와 기존 동의·토큰 검증 기준은 유지한다. 문서 확정이며 실제 앱 등록·설정·연동 검증 완료를 뜻하지 않는다.

**압축 MVP CM14(2026-10-26 사용자 승인):** 대화 시작 질문 추천(AI-01)을 P0 필수로 포함한다. 상호 수락한 활성 채팅방에서 허용된 공개 정보로 AI가 질문 3개를 제안하며, 사용자가 선택·수정해 직접 전송한다. 사용하지 않고 바로 대화할 수 있고 자동 전송하지 않는다. 공개 정보 부족·생성 실패 시 일반 질문으로 대체하며 지연 중에도 채팅을 사용할 수 있다. 비공개 설문·민감 정보 추정 금지와 종료된 방의 늦은 응답 무시를 유지한다. 고정 질문만 제공하는 방식으로 축소한 결정이 아니다. 허용 입력·생성/대체 결과 계약과 실제 구현·검증은 남는다. 기능 ID32개는 P0 29개·P1 0개·후속3개이며 AI-02 위험 감지도 CM15로 P0 유지를 확정했다.

**2026-10-22 인증·프로필 계약 대조:** 가을의 갱신 요청을 반영하고 `develop 74b2ed6`의 [인증 API 계약](https://lab.ssafy.com/s15-final/S15P31E106/-/blob/74b2ed6/docs/contracts/api/auth.md)·가입 단계/닉네임/나이/이메일 저장 코드를 확인했다. 약관 동의·7단계 응답·토큰 재발급·로그아웃은 develop에 반영되어 있다. 별도 프로필 등록 완료·등록 성공 시 생년월일/성별 고정은 [MR !26](https://lab.ssafy.com/s15-final/S15P31E106/-/merge_requests/26)의 계약과 코드에서 확인했고, 최종 재확인에서 develop 병합(`74b2ed6`, 반영 커밋 `184daf3`)도 확인했다. 최초 확인한 MR 소스 `6441435`와 병합본의 인증 계약·프로필 등록 코드가 일치한다. 이번 문서 변경은 앱 연동·실행 테스트·배포 완료를 뜻하지 않는다. 현재 브랜치에 없는 계약은 확인한 커밋의 링크로 연결한다.

로그아웃을 새 매칭/제안 중지 조건으로 사용하지 않는다. 저장된 매칭 ON/OFF를 유지하며 기존 매칭 준비/대상 조건을 충족한 ON 계정은 로그인 세션이 없어도 MAT-03을 수행하고 유효한 매칭에 KEY-06의 진동을 안내한다. 사용자 세션 종료와 매칭/진동 처리용 기기·서버 인증을 구분하는 계약이 필요하며, 비로그인 사용자에게 제안/채팅 조회·수락·전송 API 권한을 주는 것은 아니다.

로그아웃해도 계정과 해당 휴대폰 앱의 푸시 수신 연결을 유지한다. 알림이 허용되면 새 제안 생성 시 “새로운 매칭 제안이 도착했어요!”라고 안내하며, 로그아웃 중 알림에는 상대 사진·이름·채팅 내용을 넣지 않는다. 알림 선택 시 로그인 화면으로 이동하고, 해당 계정 로그인 성공 후 서버에서 권한·현재 상태를 조회해 유효한 제안을 보여준다. 로그인 실패/취소·다른 계정 로그인에는 해당 제안/프로필을 노출하지 않고 만료·종료 제안을 복원하거나 기한을 연장하지 않는다.

같은 휴대폰 앱에서 다른 계정으로 로그인하면 이전 계정의 푸시 연결을 해제한다. 수신 식별자 갱신·해제와 계정 전환 중 전송 대기/지연 알림, 로그인 후 목적지 복원·유효하지 않은 제안 안내는 가을·영빈·FE가 계약과 기기 검증에서 구체화한다. 권한 없음·통신/운영체제 제한으로 푸시가 지연·누락되어도 제안 생성과 키링 진동을 푸시 수신 성공에 종속시키지 않는다. 로그아웃 중 새 채팅 메시지 알림은 보내지 않는다. 새 제안 푸시 연결은 유지하고 알림 종류별로 수신 대상의 로그인 상태를 확인한다. 로그아웃 중 상호 수락에 따른 채팅방 생성 알림도 보내지 않는다. 방 생성은 정상 진행하고 생성 시점부터 7일을 계산하며 재로그인 때 생성 알림을 재발송하지 않는다.

서비스 이용 준비를 마친 계정이 일반 재로그인하면 홈으로 이동해 서버의 최신 제안/채팅 상태를 조회한다. 가입 미완료 계정은 AUTH-02를 따른다. 유효한 미응답 제안·내 수락 후 대기 제안은 제안 목록에, 상호 수락으로 생성된 활성 방은 채팅 목록에 표시한다. 내 결정 전 상대 응답은 계속 비공개이며 상대 선행 거절만으로 미응답·기한 내 제안을 숨기지 않는다. 종료된 제안/방은 목록과 대화에서 제외하고 캐시로 복원하지 않는다. 활성 방에는 기존 대화와 안 읽은 메시지를 표시하며 로그인/목록 조회만으로 본인의 새 메시지를 확인 완료로 처리하지 않는다. 제안 만료 시각과 방 생성 후 7일은 로그아웃 중에도 계속 흐른다.

새 제안 알림으로 로그인한 경우 해당 계정의 권한·최신 상태를 조회해 유효 제안 상세로 이동한다. 이미 상호 수락되어 활성 방이 생성됐으면 해당 방으로, 생성 중/실패면 CHAT-01의 준비/재시도 흐름으로 연결한다. 제안과 연결된 방이 모두 종료됐다면 짧게 안내하고 제안 목록으로 이동하며 상대 선행 거절 비공개 예외는 유지한다. 다른 계정에는 알림 대상 제안/대화를 노출하지 않는다. 조회 실패는 빈 목록과 구분해 불러오기 실패 안내·재시도 버튼을 표시한다. 놓친 알림을 일괄 재발송하지 않고 목록·안 읽은 표시로 안내하며, 유효한 방은 확인 단계 없이 진입하며 CHAT-03의 상단 종료 안내를 표시한다. 목적지 판단/조회 API·오류 문구·화면 전환 경합은 FE·BE 계약으로 검증한다.

### AUTH-02 가입 단계 안내와 재개

| 구분 | 기준 |
| --- | --- |
| 사용자·조건 | 로그인했지만 최초 가입 절차를 마치지 않은 회원. 기존 이용자의 마지막 키링 초기화는 별도 권한 분기 |
| 실행·입력 | 로그인 직후 또는 앱 재진입 시 서버에 완료 상태 확인 |

| 완료 기준 | 필수 약관 미동의·키링 미등록·필수 입력 누락·설문 미완료·설정 미동기화 각각에서 올바른 단계로 복귀. 설문 1~10번 저장 후 앱 종료·재로그인 시 재개 확인, ‘예’ 선택 후 응답 복원·11번부터 재개 |

설문 제출 후 계산 대기·진행·실패는 `SURVEY_REQUIRED` 안의 별도 처리 상태로 구분한다. `SURVEY_PROCESSING`을 가입 단계 enum으로 추가하지 않는다. 답변을 저장한 채 처리 안내/분석 재시도를 제공하고 앱 재진입에도 설문을 다시 쓰게 하지 않는다. 최초 분석 성공 후 희망 나이 단계로 진행하며 이미 유효한 결과가 있는 재검사는 기존 결과를 유지한다. 처리 상태의 실제 필드·조회/재시도 API는 영빈·가을·FE가 DES03에서 연결한다.

기존 이용자가 마지막 키링을 초기화한 뒤 재진입/재로그인한 경우 신규 매칭 준비와 기존 기능 권한을 분리한다. 등록 기기 0개여도 홈·기존 유효 제안/프로필 조회·수락/거절·활성 채팅·탈퇴 접근을 키링 등록 화면으로 가로막지 않는다. 키링 미등록과 등록 경로를 안내하고 신규 매칭은 재등록/동기화 등 준비 완료 전까지 보류한다. 기본 정책의 최초 가입·재가입에는 필수 등록 절차를 적용한다.

**가입 완료 회원의 기존 제안 접근(2026-10-22 영빈 회신):** `signupCompleted=true`인 회원은 마지막 키링 초기화나 AI 동의 철회만으로 가입 화면에 되돌리지 않는다. `matchingReady`는 새 매칭 준비 여부이며 기존 유효 제안 조회·수락·거절 권한을 대신하지 않는다. FE와 BE 모두 기존 제안 권한을 새 매칭 준비 검사와 분리한다. 만료·차단·탈퇴·연령 미달 확인에 따른 이용 제한 등 기존 제한은 유지한다. AI 동의 철회 시 채팅 이용 제한/재동의·이미 종료된 방 미복원은 유지하며, 이 예외를 다른 필수 약관 미동의까지 확대하지 않는다. 키링이 없는 경우의 새 매칭 보류와 AI 철회 중 새 매칭에 대한 기존 정책도 각각 유지한다.

#### 서버별 가입 키링 요구

백엔드는 서버 설정 `TINGLE_SIGNUP_KEYRING_REQUIRED`를 모든 계정의 가입에 동일하게 적용한다. 기본값인
`true`(또는 `on`·`yes`·`1`)에서는 `REQUIRED`, `false`(또는 `off`·`no`·`0`)에서는 `OPTIONAL`을 반환한다. 운영과 개발은 각각 독립적으로 설정할 수
있고, 앱 요청으로 정책을 변경할 수 없다. 서버 안에서는 `app.signup.keyring-required` 속성으로 읽으며 값은
기동할 때 한 번 정해진다. 키링 없이 가입하면 희망 조건 저장이 마지막 단계이므로 저장 성공 시 가입 완료 시각을 기록한다. 불리언으로 해석할 수 없는 값이면 서버가 기동하지 않는다(`OPTIONAL`로 바뀌지 않는다).

Compose/Jenkins에서 운영 배포는 `TINGLE_PROD_SIGNUP_KEYRING_REQUIRED`, 개발 배포는
`TINGLE_DEV_SIGNUP_KEYRING_REQUIRED`를 각각 해당 백엔드의 `TINGLE_SIGNUP_KEYRING_REQUIRED`로 전달한다.
두 배포 입력의 기본값은 모두 `true`다. 변경한 배포 입력으로 Compose 설정을 렌더링하고 해당 백엔드
컨테이너에 새 환경을 적용한 뒤부터 정책이 바뀐다. 기존 컨테이너를 그대로 재시작하면 이전 환경을 사용한다.
롤백에서 기존 컨테이너를 다시 시작하는 경우에도 저장된 환경을 사용한다.

| 시점과 조건 | 현재 가입 단계와 가입 이력 |
| --- | --- |
| `REQUIRED`, 필수 약관 동의 후 키링 미등록 | `KEYRING_REQUIRED`. 이후 키링 등록과 최신 설정 ACK를 포함한 기존 순서 적용 |
| `OPTIONAL`, 약관·프로필·설문·희망 조건 중 누락 | `AGREEMENT_REQUIRED → PROFILE_REQUIRED → SURVEY_REQUIRED → PREFERENCES_REQUIRED` 중 최초 미완료 단계 반환. 설문 분석 등 기존 완료 조건 적용 |
| `OPTIONAL`, 키링 외 모든 가입 조건 충족 | 소유·최신 설정 ACK 없이 `READY`. 첫 완료 시각을 한 번 기록하고 일반 가입 완료 회원 기능 이용 가능. 키링 미보유 상태에서는 `matchingReady=false` |
| 키링 요구 재활성화, 최초 가입 완료 전 | `REQUIRED`로 재계산. 약관 미동의가 없다면 키링 미등록 시 `KEYRING_REQUIRED`, 등록 후 다른 가입 조건을 모두 충족하고 최신 ACK가 없으면 `SYNC_PENDING`. 저장한 진행 내역 유지 |
| 키링 요구 재활성화, 최초 가입 완료 후 | `REQUIRED`로 재계산. 현재 미충족 단계에서는 `onboardingCompleted=false`가 될 수 있다. `signupCompleted=true`와 기존 완료 시각을 보존하며 홈·유효 제안·채팅 등 기존 기능은 AUTH-02와 각 기능의 권한 규칙 적용 |

가입 완료 이력, 등록 키링 소유 상태, 신규 만남 제출 권한을 따로 판정한다. 새 기기 작업과 만남 접수는 요청마다
기존 인증·서명·소유권·설정 버전 등 해당 기능의 현재 조건을 확인한다. `OPTIONAL`이나 `READY`는 키링 등록 증명,
동기화·초기화 서명 또는 키링·휴대폰 만남 제출 자격을 부여하지 않는다.

**온보딩 조회 예시**

```http
GET /api/users/42/onboarding HTTP/1.1
Authorization: Bearer <accessToken>
```

요청 본문은 없다. 경로의 회원 ID와 인증된 회원이 일치해야 하며, 인증과 본인 확인 오류 응답은 기존 계약을
따른다. 아래는 키링 요구가 꺼진 서버에서 키링 없이 가입을 완료한 회원의 `200 OK` 응답에서 변경과 관련된 필드를 발췌한 예시다.

```json
{
  "nextStep": "READY",
  "keyringRequirement": "OPTIONAL",
  "signupCompleted": true,
  "onboardingCompleted": true,
  "matchingReady": false,
  "acknowledgedSettingsVersion": null
}
```

같은 서버에서 키링 요구를 다시 켠 뒤 같은 회원이 조회하면 아래와 같다. 가입 완료 시각은 재조회나 재시도로 바뀌지 않는다.

```json
{
  "nextStep": "KEYRING_REQUIRED",
  "keyringRequirement": "REQUIRED",
  "signupCompleted": true,
  "onboardingCompleted": false,
  "matchingReady": false,
  "acknowledgedSettingsVersion": null
}
```

`keyringRequirement`는 이 조회 응답에 추가되는 필수 문자열이며 값은 `REQUIRED` 또는 `OPTIONAL`이다.
기존 필드와 단계 이름은 유지한다. 현재 앱 소스의 응답 파서는 알 수 없는 필드를 무시하며, 세션은
`nextStep`과 `signupCompleted`를 읽는다. 따라서 기본 정책에서 기존 키링 가입의 응답 형식은 호환된다.
앱은 새 필드를 읽어 안내 문구를 바꾸려면 별도 대응이 필요하다. 이전 서버에서 필드가 없으면 새 앱은
`REQUIRED`로 해석한다. 키링 없이 가입할 때 각 화면이 서버 단계에 따라 전환되는지는 앱 빌드로 확인한다.

**FE 검증 항목**

- 로그인 직후와 앱 재진입 시 서버의 최신 `nextStep`으로 화면을 결정한다. `OPTIONAL`이어도 누락된 약관·프로필·설문·희망 조건 화면을 유지하고, 키링만 남은 경우 `READY`로 진입한다.
- 키링 요구를 다시 켠 뒤 재조회에서 현재 단계와 최초 가입 완료 여부를 각각 반영한다. 최초 가입 미완료는 서버가 알려준 단계부터 재개한다. 이미 완료한 회원의 기존 기능은 재가입 화면으로 가로막지 않는다.
- 키링 미보유 `READY`에서 `matchingReady=false`를 확인하고 기기 연결·동기화 성공이나 만남 제출 자격으로 표시하지 않는다. 조회 실패에는 기존 오류·재시도 UX를 적용한다.
- 새 필드를 모르는 앱과 필드를 생략하는 이전 서버를 각각 대조하고, 기본 정책에서 키링 등록·동기화 ACK를 포함한 가입 흐름을 확인한다.

### AUTH-03 키링 보유 확인과 회원 탈퇴

탈퇴 조건 조회는 가입 단계와 관계없이 본인 계정에서 접근할 수 있어야 한다. 현재 연결된 키링이 있거나 완료 증명이 없는 초기화 작업이 있으면 각각의 제한 사유를 구분한다. 초기화 명령의 유효시간 만료는 초기화 완료가 아니며, 초기화 기능을 일시 중지해도 기존 미완료 작업을 없는 것으로 처리하지 않는다. 소유 정보와 기기 상태가 불일치해도 소유 연결이 남아 있으면 탈퇴를 허용하지 않는다. 다른 회원의 조건은 조회할 수 없다.

조회 결과는 조회 시점의 안내이며 탈퇴 실행의 사전 승인이나 완료 증명이 아니다. 최종 실행에서는 회원 행 잠금 아래 소유 및 초기화 조건을 다시 검사해야 한다. 조회 응답을 캐시하여 실행 조건으로 재사용하지 않는다. 키링과 초기화 정보 조회가 실패하면 오류로 응답하고 탈퇴 가능으로 추정하지 않는다.

| 구분 | 기준 |
| --- | --- |
| 사용자·조건 | 로그인한 탈퇴 희망 회원 |
| 실행·입력 | 설정 → 계정 관리 → 회원탈퇴. 서버의 등록 키링 조회 후 0개이면 최종 안내와 돌아가기/회원탈퇴 선택. MVP 탈퇴 사유 입력 생략 |
| 정상 동작·결과 | 등록 키링이 0개이면 일반 탈퇴 진행. 남아 있으면 초기화/키링 관리 안내, 분실이면 서비스팀 문의. 성공 시 새 매칭/안내 중지·양쪽 제안/채팅 종료·프로필 접근 차단·모든 세션/푸시 연결 해제, 완료 안내 후 로그인 화면 |
| 예외 | 소유 상태 조회 실패를 0개로 간주하지 않음. 탈퇴와 신규 키링 등록의 동시 요청으로 조건을 우회하지 않음. 분실 문의 접수만으로 탈퇴 완료 처리하지 않음 |
| 완료 기준 | 키링 0개/1개·조회 실패 분기(기존 복수 데이터 전환은 별도), 마지막 초기화 후 탈퇴 화면 접근 유지. 성공 후 양쪽 목록/프로필/대화 접근 종료와 세션/푸시 해제. 응답 유실 시 상태 확인·중복 종료 방지, 서비스팀 탈퇴에도 공통 종료 처리, 분실 기기는 KEY-04 차단 적용. 정정 과정에서 만 19세 미만 확인 시 일반 이용 제한·초기화/문의와 필요한 인증 접근 유지. 매칭·제안 수락·채팅 이용 중지, 상대방 공통 이용 불가 안내·사유 비공개·수락/메시지 전송 제한. 인증/상태 전환 경합은 별도 계약. CM16으로 24시간 대기 후 자동 탈퇴·초기화 마감·미초기화 기기 차단·기산/카운트다운은 현재 완료 기준에서 제외하며 즉시 강제 탈퇴로 대체하지 않음. 이후 운영 처리 시점·완료 조건은 별도 협의 |
| 데이터·검토 | 등록 기기 수·탈퇴 요청/처리 상태. 서비스팀 확인·권한·처리 기록, 회원 데이터 삭제 방식/완료 기한·혼재 기기 부분 실패/동시 처리 계약은 별도 검토. 정상 기기 초기화 후 분실 기기 차단/탈퇴 순서는 KEY-04의 확정 기준 적용. 탈퇴 처리 가을, 기기 종무·재준, 제안/채팅 종료 영빈·순철 연동. 문의 응대 창구는 재준, 실제 처리 권한/범위는 POL07·DES11에서 확인 |

최종 확인에는 프로필 비공개 전환·모든 진행 중 제안/채팅 종료·종료 항목 재이용 불가·기록은 안내된 보관 기준에 따른다는 정책 §4.1의 문구를 표시한다. 키링이 있으면 “탈퇴하려면 등록된 키링을 모두 초기화해 주세요.”와 ‘키링 관리하기’, 분실이면 ‘서비스팀 문의하기’, 소유 조회 실패면 오류와 ‘다시 확인하기’를 제공한다. 마지막 키링을 초기화해도 탈퇴 화면을 이용할 수 있어야 하며 키링 재등록 화면으로 강제 이동시키지 않는다.

탈퇴 완료 시 기존 제안은 양쪽 목록에서 제거하고 공개 프로필 조회·수락을 막는다. 미응답자의 상대 응답 비공개 규칙을 이유로 탈퇴한 계정의 제안/프로필을 계속 열어두지 않는다. 활성 채팅방은 7일이 남아도 양쪽에서 즉시 종료하고 목록·대화를 제거한다. 열린 방에서는 “이 대화는 종료됐어요.” 안내 후 채팅 목록으로 이동한다. 상대에게 탈퇴 사실/사유를 표시하거나 탈퇴 푸시를 보내지 않는다. 해당 계정의 새 매칭·키링 안내를 중지하고 모든 로그인 세션과 푸시 수신 연결을 해제한다. 서버 성공 확인 후 “회원탈퇴가 완료됐어요.”를 표시하고 로그인 화면으로 이동한다.

채팅은 탈퇴로 인한 실제 종료일부터 30일 보관 후 삭제한다. 이미 종료된 방의 기한을 다시 시작하지 않는다. 응답 유실은 실패로 단정하지 않고 처리 상태를 확인하며, 재시도로 탈퇴·방 종료를 중복 처리하지 않는다. 서비스팀 강제 탈퇴에도 동일한 서비스 종료/세션/푸시 해제를 적용하고 분실 기기는 KEY-04대로 영구 사용 불가로 처리한다. 탈퇴와 등록/수락/방 생성/전송/알림 발송 경합, 세션 해제 후 결과 확인, 캐시·지연 이벤트 처리는 FE·BE 계약에서 검증한다. 회원 데이터 삭제 범위·재가입 시 새 가입 ID 발급과 미복구 기준은 아래를 따른다.

재가입 제한은 서버의 탈퇴 완료 시점부터 3일(72시간)이다. 72시간 전에는 제한 안내와 재가입 가능 날짜·시각을 표시하고 해당 시각부터 재가입을 허용한다. 탈퇴 처리 재시도/로그인 시도로 기한을 갱신하지 않는다. 이는 일반 채팅 30일/신고 기록 보관과 별개다. 동일 소셜 계정 대조용 최소 정보와 보관/삭제는 아래 기준을 따른다. 다른 소셜 계정/제재 처리는 후속 계약으로 정한다. 별도 운영 제재·분실 키링 영구 차단은 72시간 경과로 해제하지 않는다.

탈퇴 성공 시 접근을 즉시 차단하고 프로필(닉네임·소개·생년월일·성별·흡연·음주·종교)·연락용 이메일, 사진 원본/가공본/썸네일, 설문 완료/임시/과거 재검사 응답, 점수/성향 벡터/개인별 매칭 설명 등 분석 결과, 희망 나이/사진 필수 옵션/매칭 설정을 지체 없이 삭제한다. 로그인 토큰을 무효화하고 저장된 토큰/푸시 수신 정보도 삭제한다. 기존 사진 주소로 조회할 수 없도록 하며, 캐시·백업·분석 사본을 삭제 대상에서 누락하지 않는다. 삭제 실패는 재시도하고 저장소별 완료를 확인하며, 백업 복원이나 지연 작업으로 삭제 데이터를 다시 노출하지 않는다. 방식·완료 기한·오류/복원 검증은 BE·AI·FE·인프라 계약에서 정한다.

일반 채팅 보관과 분실 기기 영구 사용 불가 식별 정보는 기존 기준을 유지한다. 채팅 보관을 이유로 별도 프로필/사진/설문/분석 결과를 남기지 않는다. 대화에 직접 작성한 정보는 대화 기록의 기한을 따른다. 재가입 제한용 최소 정보는 아래의 72시간 기록을 따르고, 동의/운영 이력은 별도 보관 계약으로 정한다. 최종 탈퇴 안내에는 이 삭제 범위·재가입해도 미복구·72시간 후 재가입 가능·별도 채팅 보관과 아래의 재매칭 제한용 최소 기록 1년 보관을 설명한다.

재가입은 같은 소셜 계정이어도 새 서비스 가입 ID로 시작한다. 키링 등록·프로필·설문·희망 조건·동기화 준비를 다시 진행하고, 이전 프로필/사진/설문/분석 결과/설정/제안/채팅을 새 계정으로 복구하거나 연결하지 않는다. 정상 초기화한 키링은 재등록 가능하지만 영구 사용 불가 기기는 불가다. 별도 운영 제재를 자동 해제하지 않으며 다른 소셜 계정의 동일인 식별/제재 우회 처리는 별도 계약으로 남긴다.

재가입 제한 기록은 일반 회원 데이터와 분리해 소셜 제공자·서버 비밀키를 이용한 HMAC 계정 대조값·재가입 가능 시각 세 항목만 72시간 보관한다. 원본 소셜 고유번호·이름·이메일·전화번호·생년월일·사진·설문·이전 가입 ID·로그인 토큰을 이 기록에 넣지 않는다. 대조값도 보호 대상 식별 정보로 취급하고 비밀키를 기록과 분리해 관리한다. 최종 탈퇴 화면에는 “반복 가입을 방지하기 위해 소셜 로그인 제공자, 계정 대조값, 재가입 가능 시각을 탈퇴 후 3일간 보관한 뒤 삭제해요.”를 안내한다.

서버가 검증한 소셜 인증 결과로 제공자와 고유 식별값의 HMAC을 계산해 대조한다. 임의 이메일/번호·검증되지 않은 클라이언트 식별값으로 판단하지 않는다. 만료 전에는 재가입 가능 시각을 안내하고, 만료 시각부터 새 가입을 허용한다. 기록은 만료 시 자동 삭제·실패 재시도·완료 확인하며, 삭제 지연 중에도 만료된 기록으로 제한하지 않는다. 재시도로 기간 연장이나 별도 유예기간을 추가하지 않는다. 로그/캐시/백업의 불필요한 잔존과 복원 시 재노출을 막는다. 신고/제재/분실 기기 기록으로 전용하거나 보관을 연장하지 않는다.

보관 목적·항목·기간과 처리 근거는 개인정보 처리 안내에 명시한다. 가을은 제공자별 연결 해제/재동의 후 식별값 대조 가능 여부·인증 검증·HMAC 키 관리와 교체·삭제 작업을 검증한다. 탈퇴 성공과 제한 기록 저장, 조회/삭제 실패·동시 가입의 일관성은 FE·BE 계약으로 정한다. 다른 소셜 계정의 동일인 식별은 이번 범위가 아니다.

**재가입 후 재매칭 제한 유지(2026-10-21 사용자 결정):** 한쪽이 탈퇴·재가입해도 기존 상대와의 재매칭 제한을 초기화하지 않는 방향을 확정한다. 기존 나가기(AI 동의 철회 포함)·7일 종료의 재매칭 금지와 유효한 차단 관계를 새 가입 ID에서도 적용할 수 있도록 최소 식별/관계 계약을 별도로 마련한다. CM11로 사용자 차단 해제는 MVP에서 제공하지 않지만 기간이 정해진 제한의 종료/삭제 기준을 무기한으로 바꾸지 않는다. 새 계정 발급 및 프로필·사진·설문·설정·제안·채팅 미복구는 유지하며, 제한 적용에 필요한 최소 대조만 예외로 검토한다. 대화 내용이나 과거 프로필을 복원하는 기능으로 사용하지 않는다.

3일(72시간) 재가입 금지 기록과 재매칭 제한 유지 기록은 목적과 수명을 구분한다. 기존 72시간 기록의 삭제 기한을 늘리거나 해당 기록을 다른 목적으로 전용하지 않는다. 72시간이 지나면 계정 재가입 자체는 허용하고, 재가입 후에도 제한된 상대는 새 매칭·제안·진동에서 제외하는 것이 목표다. 보관 기간은 아래의 탈퇴 후 1년으로 확정하며, 추가 최소 식별값·관계/사유·기간 정보와 처리 근거는 POL03의 잔여 검토 후 실제 저장에 적용한다. 이번 결정만으로 무기한 보관·실명/전화번호/신분증 수집을 허용하지 않는다.

가을·영빈이 검토할 설계안은 검증된 소셜 제공자·계정 식별값을 이용한 별도 목적의 서버 HMAC 대조값과 최소 관계 정보를 사용하는 방식이다. 이는 확정 DB 스키마가 아니며 72시간 가입 제한용 키/기록과의 목적 분리·키 교체·탈퇴/재가입 동시 처리·관계 삭제/복원·접근 권한을 함께 검토한다. 대조값은 익명정보로 간주하지 않는다. 현재 서로 다른 소셜 계정은 자동 통합하지 않으므로 다른 제공자/새 소셜 계정으로 가입한 동일인까지 알아보는 기능은 보장하지 않는다. 동일 소셜 계정도 제공자의 연결 해제/재동의 후 식별값 안정성을 검증해야 한다. 더 넓은 동일인 식별이 필요하면 수집 범위와 운영 정책을 별도로 결정한다.

**탈퇴 후 보관 기간(2026-10-21 확정):** 재매칭 제한 유지에 필요한 최소 대조값·관계 기록은 서버의 탈퇴 완료 시각부터 1년간 보관한다. 재가입·조회·분석/삭제 재시도로 기존 기록의 기한을 다시 시작하지 않는다. 같은 제한을 새 가입 ID로 옮겨 적는 방식으로 기한을 연장하지 않는다. 예를 들어 2026년 10월 21일 15:00 탈퇴 기록은 2027년 10월 21일 15:00에 만료하며, 그 전에 재가입해도 이 기한을 유지한다. 만료 시 해당 탈퇴 기반의 대조/관계 기록을 삭제하고 이를 근거로 이어 붙인 제한도 종료한다. 삭제 지연·백업 복원으로 만료된 제한을 다시 적용하지 않는다. 두 계정이 계속 유지되는 경우의 기존 재매칭 금지와 별도로 발생한 유효한 제한은 해당 기존 정책을 따른다. 이 1년은 채팅 본문·프로필·사진·설문 보관 기간을 늘리는 근거가 아니다.

남은 사항은 최소 저장 항목·식별 적용 범위/처리 근거 확인과 BE 구현 계약이다. 가을·영빈은 양쪽 탈퇴·재가입/재탈퇴·윤일 경계·키 교체·삭제/복원 시에도 같은 기존 관계의 기한을 늘리지 않는 방식을 설계하고 검증한다. 회원탈퇴 안내와 개인정보 처리 안내에는 실제 확정된 항목·목적·기간·미복구와 제한 유지의 차이를 반영해야 하며, 확정 전 '모든 식별 정보가 3일 후 사라진다'거나 '재가입 제한 유지가 구현됐다'고 안내하지 않는다.
