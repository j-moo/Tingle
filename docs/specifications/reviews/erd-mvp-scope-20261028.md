# ERD 기준 MVP 범위 — 2026-10-28

## 확정한 범위

사용자 결정: “ERD관련은 MVP라고 생각하자.”

현재 공유된 21테이블 ERD가 표현하는 기능은 MVP에 포함한다. 신고 접수·메시지 증거 연결·운영 신고 검토·신고 보관을 후속으로 미루던 CM09 범위 결정을 대체한다. ERD 상단의 과거 ‘운영/지원은 MVP 밖’ 주석도 이번 범위 판단의 근거로 사용하지 않는다.

이것은 기능 범위 결정이다. 테이블 존재를 실제 API·화면·배포 완료로 취급하지 않으며, ERD의 변경 이력·‘합의 필요’·무결성 문제까지 해결된 것으로 표시하지 않는다. ERD에 별도 테이블이 없다는 이유로 기존 필수 기능을 삭제하지 않는다. 기존 기능 ID는 유지하며 신고는 SAFE-01·CHAT-06·운영 범위에 다시 포함한다.

## ERD와 MVP 기능 연결

| ERD 테이블 | MVP 기능 |
| --- | --- |
| users, refresh_token, push_installation | 회원·가입·인증 세션·기기/푸시 연결 |
| profile, matching_preference, user_setting | 프로필·희망 조건·키링 출력/설정과 동기화 버전 |
| survey, survey_answer, personality | 설문 회차·문항 저장/재개·분석 상태/결과 |
| keyring | 키링 소유·등록/해제·동기화 |
| matching, matching_participant | 만남·제안·개인별 수락/거절·차단 관계 |
| chat, chat_participant, chat_message | 채팅방·참여·메시지·새 메시지 상태·종료 |
| chat_report, chat_report_message | 사용자 신고·신고 사유/상세·증거 메시지 연결 |
| chat_safety_notice | 개인 위험 안내·수신 대상·실제 표시 상태 |
| service_case, service_case_history, operator_audit | 정정/분실 지원·처리 이력·운영 권한/접근 감사 및 신고 검토 |

테이블마다 화면을 하나씩 만드는 의미는 아니다. 사용자 행동·권한·상태를 기준으로 화면과 API를 묶는다.

## 신고에 적용할 현재 기준

- 채팅방 문맥에서 신고 사유·선택 상세·증거 메시지를 제출하는 기능을 포함한다. 현재 ERD의 ABUSE/SEXUAL/SPAM/ETC와 RECEIVED/REVIEWING/RESOLVED/DISMISSED는 BE 응답 계약으로 정합화한다.
- 서버는 현재 신고자와 방 참여자, 선택 메시지가 같은 방에 속하는지 검증한다. FE는 신고 API 성공 응답 전 접수 완료로 표시하지 않는다.
- 운영자는 권한이 있는 신고 목록/상세·증거/대화·처리 상태를 조회/처리하며 해당 접근·작업을 감사 기록으로 남긴다. 일반 사용자의 종료 채팅 재조회나 운영자의 무제한 전체 대화 검색으로 확대하지 않는다.
- ERD의 `chat.retain_until` 기준으로 신고된 방 전체 메시지는 최초 신고부터 90일 보관하는 분기를 포함한다. 메시지 선택은 검토 지점 표시이며 선택 메시지만 보관하는 뜻이 아니다. 재신고·재시도로 최초 기산을 연장하지 않는다.
- 방 종료 시 사용자 조회/전송 종료는 보관과 별개다. 보관 중 탈퇴의 참조 정리, 일반 삭제와의 우선순위, 구 명세의 기각 후 단축 보관과의 차이를 서버 삭제 계약에서 명시한다. 현재 실제 데이터의 삭제를 실행하라는 결정은 아니다.
- AI 위험 안내의 ‘신고 기능을 이용’ 문구는 MVP 범위상 허용한다. 실제 신고 UI/API가 연결되기 전 가상 화면임을 구분하고, 동작하지 않는 신고 경로를 완성 기능처럼 노출하지 않는다.
- AI 감지만으로 자동 신고·자동 제재하지 않는다. 신고 운영 검토와 AI가 신고 처리 우선순위를 매기는 AI-03은 별개이며, ERD에 근거가 없는 AI-03 자동 추가는 하지 않는다.

## 남은 구현 계약

공개 API의 ID·경로·권한·응답은 BE 영빈이 확정하고 AI 성현과 FE 재준이 맞춘다. 숫자 ID·/api 초안을 우선 협의 기준으로 삼되 기존 /api/v1·UUID와의 적용 범위/전환 시점을 확인한다.

신고 POST/조회·운영 처리 경로, 사유 코드·상세 길이·메시지 선택 한도·중복/응답 유실·종료 방 접수 가능 범위·보관/탈퇴 참조 무결성을 명시해야 한다. 기존 BE 86번은 과거 24테이블 계약이므로 21테이블 기준 재대조가 필요하다.

재매칭, 복수 키링/초기화, 일괄 동의와 선택/철회, 일반 채팅의 탈퇴 시 삭제 등 ERD와 과거 문서의 동작 차이는 상세 정합화 대상으로 기록한다. 기능 포함 승인을 이유로 기존 상태/동의를 무시하거나 충돌하는 과거 주석을 임의로 실행하지 않는다.

## 수용 기준 — 실행 전

- 정상 신고 접수·권한 없는 방 거부·다른 방 메시지 거부·빈/잘못된 입력 처리.
- 응답 유실/동시 중복 신고의 실제 접수 상태 복구와 기산 시각 보존.
- 운영자 권한 검사·조회/처리 감사·일반 사용자에게 운영 정보 비공개.
- 최초 신고+90일 경계, 반복 신고·탈퇴·일반 삭제 작업 경합과 보관 관계 유지.
- 위험 안내의 신고 진입은 사용자 행동으로만 수행하고 자동 신고를 만들지 않음.
- 문서/정적 검토, 가상 화면, 실제 서버 테스트, MR 승인/병합을 구분한다.
