사용자는 소셜 로그인과 키링 등록을 마친 뒤 프로필·성향테스트·희망 조건을 입력한다. 매칭 제안에서 상대 프로필을 확인하고 서로 수락하면 7일 동안 대화한다. 이 명세는 각 단계의 실행 조건, 기대 동작, 예외와 검증 기준을 정리하여 화면·API·ERD 설계의 공통 출발점으로 사용한다.

## 1. 읽는 방법과 적용 범위

- **확정:** 사용자와 합의한 서비스 동작. 구현 담당자가 임의로 바꾸지 않는다.
- **임시:** 앱 골격 개발에 사용하는 기존 초안·v8 기준. 최종 정책이나 검증된 추천 성능으로 표현하지 않는다.
- **검토:** 아직 결정하지 않은 정책 또는 구현 방식. 예시를 확정값으로 사용하지 않는다.
- 아래 **완료 기준은 앞으로 확인할 기대 결과**다. 통과한 테스트 결과가 아니다.
- 목록의 ‘필수안/선택안’은 이번 기능 분류의 우선순위 초안이다. 가입 입력의 필수/선택 여부와는 다른 의미이며 PM·팀 검토 후 확정한다.
- 기능별 ‘협업/작업’은 검토·연결 관계다. 기존 계약 담당에게 관련 기능 전체 구현을 자동 배정하지 않는다. 종료 안내 구현만 BE 영빈(49)·FE 순철(50)로 별도 확정되어 있다.

공통 데이터 이름은 API·ERD에서 다뤄야 할 정보의 예시다. 엔드포인트, 필드명, 테이블명, DB 타입과 인덱스는 각 담당 계약에서 정한다. 상세 입력 규칙은 기준 정책의 §2, 진입 상태는 §4, 제안·채팅은 §5, AI 범위는 §7을 함께 확인한다. 규칙 변경 시 정책과 이 명세를 함께 갱신한다.

기존 계획서의 Req.1~16 및 수용 테스트 23개와의 일대일 대응은 26번에서 원본을 대조해야 한다. 이 초안의 기능 ID를 기존 요구사항 번호로 간주하지 않는다. 서버 위치 미저장·회전 임시 ID·키링 24시간 동작 등 26번의 비기능 요구사항도 별도 추적한다.

## 3. 기능별 동작 명세

### AUTH-01 소셜 로그인

| 구분 | 기준 |
| --- | --- |
| 사용자·조건 | 비로그인 사용자 또는 인증이 필요한 기존 회원 |
| 실행·입력 | 구글·카카오·네이버 중 하나로 로그인. 제공자가 발급한 인증 정보를 서버에서 검증 |
| 정상 동작·결과 | 인증된 계정과 연결하고 현재 가입 단계로 이동. 초기 버전에서는 서로 다른 소셜 계정을 자동 통합하지 않음. 계정 식별 정보는 상대에게 공개하지 않음 |
| 예외 | 로그인 취소·제공자 오류·검증 실패 시 로그인 완료로 처리하지 않고 재시도 안내. 이메일·이름이 같다는 이유로 다른 소셜 계정의 프로필·키링·설문·채팅 기록을 자동 연결하지 않음 |
| 완료 기준 | 세 제공자의 정상·취소·실패를 구분하고, 검증되지 않은 정보로 회원 기능에 접근할 수 없음. 다른 제공자에서 같은 이메일을 반환해도 계정·데이터가 자동 통합되지 않음 |
| 데이터·검토 | 회원·소셜 연결·인증 상태. 토큰/재발급·로그아웃 상세는 35·45번 계약. 수동 계정 연결·통합 기능의 제공 여부는 별도 검토이며 이번 확정에 포함하지 않음 |

### AUTH-02 가입 단계 안내와 재개

| 구분 | 기준 |
| --- | --- |
| 사용자·조건 | 로그인했지만 서비스 이용 준비를 마치지 않은 회원 |
| 실행·입력 | 로그인 직후 또는 앱 재진입 시 서버에 완료 상태 확인 |
| 정상 동작·결과 | 키링 → 프로필 → 설문 → 희망 조건 → 동기화 순으로 미완료 단계 안내. 이미 저장한 입력 복원. 설문은 문항별 임시 저장된 응답을 복원하고 다음 미응답 문항부터 재개 |

| 완료 기준 | 키링 미등록·필수 입력 누락·설문 미완료·설정 미동기화 각각에서 올바른 단계로 복귀. 설문 1~10번 저장 후 앱 종료·재로그인 시 응답을 복원하고 11번부터 재개 |
| 데이터·검토 | 단계별 완료 여부·동의 버전·다음 단계. 회원가입 완료와 매칭 준비 완료의 정확한 상태명은 35번과 합의 |

## 4. API와 ERD 설계에 넘길 정보

아래는 설계 확인 목록이다. API와 DB 구조를 확정한 표가 아니다. 한 기능이 여러 API·테이블을 사용할 수 있고, API 응답은 DB 행을 그대로 공개하지 않는다.

| 기능 묶음 | 필요한 API 동작 | ERD에서 관계를 검토할 정보 | 확인할 경계 |
| --- | --- | --- | --- |
| AUTH·KEY | 로그인 검증·단계 조회·등록·동기화 확인 | 회원↔소셜 연결, 회원↔키링 연결, 동의/단계/설정 버전 | 등록 소유 증명·재등록·단계 우회 |
| PRO | 본인 저장·사진 처리·제안용 공개 조회 | 회원↔프로필/사진, 공개 응답과 원본 구분 | 생년월일 비공개·삭제 사진 캐시 |
| SUR | 문항/응답 저장·결과 조회 | 설문 버전↔문항↔응답↔성향 결과 | 새 프로필 값과 v8 원응답 분리 |

| PROP | 목록/상세·수락/거절·만료 | 제안↔당사자별 응답↔채팅 연결 | 응답 동시성·24시간 경계·이전 사진 옵션 유지 |

API 담당자는 기능 ID를 API 문서에 연결하고 요청·응답·권한·오류 샘플을 적는다. ERD 담당자는 데이터의 소유자·관계·유일성·시간 기준·삭제 순서를 검토한다. 예를 들어 첫 입장 안내는 방 전체 값 하나가 아니라 **방마다 사용자별로 구분되는 상태**가 필요하다.
