# Jira 컨벤션

v0.6.0, 2026.10.19 (소개팅 앱·IoT 팀 구성, 공통 명세와 비코드 작업 완료 기준 반영)

키링과 앱을 연결하는 소개팅 서비스 6인 팀의 Jira 사용 규칙이다. 각 규칙에는 `[rule-id]` 를 붙여서 리뷰나 회의에서 링크로 가리킬 수 있게 한다. Jira 프로젝트 키는 `S15P31E106` 이다 (https://ssafy.atlassian.net). 저장소 작업과 리뷰는 [GitLab 컨벤션](gitlab-convention.md)을 따른다.

## 팀 역할

| 팀원 | 역할 | 협업 책임 |
| --- | --- | --- |
| 재준 | PM·FE | MVP 범위·우선순위·완료 기준 조율, 앱 개발 |
| 순철 | 팀장·FE | 팀 협업 규칙·도구 설정 관리, 앱 개발 |
| 영빈 | BE | 서버·데이터·API 개발 |
| 가을 | BE | 서버·데이터·API 개발 |
| 성현 | AI | 자연어 구조화·매칭 규칙 설계와 검증 |
| 종무 | IOT | 키링 펌웨어·통신·동기화와 실기기 검증 |

구체적인 기능 담당은 Story마다 정한다. PM과 팀장은 별도 역할이며, PM은 스프린트 조율을, 팀장은 협업 환경과 규칙 운영을 맡는다. AI는 온라인에서 자연어를 구조화하고, IOT는 키링에서 실행할 경량 매칭 규칙을 AI와 함께 맞춘다. 부품 도착 전에는 공통 명세·가상 키링·테스트 데이터를 준비한다.

## 이슈 타입

### Epic 과 Story 2가지 타입만 쓴다
_[issue-hierarchy]_

Task, Bug, Sub-task 는 만들지 않는다. 설정·조사·문서 작업과 버그도 모두 Story 로 만들고, 종류는 라벨로 구분한다(`[fixed-labels]`).

| 타입 | 언제 쓰나 | 크기 |
| --- | --- | --- |
| Epic | 기능 덩어리, 또는 8포인트를 넘는 일. 포인트 없음 | 하위 Story 합계 |
| Story | 담당자 한 명이 끝낼 수 있는 모든 일 | 1포인트~8포인트 |

### 모든 Story 는 Epic 하나에 연결한다
_[link-to-epic]_

Epic 이 없는 Story 는 스프린트에 넣지 않는다.

### Story 하나에는 담당자 한 명, 파트 하나만 둔다
_[one-owner-story]_

여러 파트가 걸린 기능은 파트별 Story 로 나누고, 같은 Epic 에 넣은 뒤 "relates to" 링크로 서로 연결한다. Sub-task 로 쪼개지 않는다.

나쁜 예:

```
[BE/FE] 익명 제안 수락 구현        ← 파트 두 개, 담당자가 애매함
```

좋은 예:

```
[BE] 익명 제안 수락 API 구현
[FE] 익명 제안 수락 화면 구현     ← 위 Story 와 relates to 로 연결
```

## 이슈 제목

### 제목은 `[파트] 무엇을 한다` 형식으로 쓴다
_[title-format]_

파트 태그는 `[AI]` `[BE]` `[FE]` `[IOT]` `[INFRA]` `[DOC]` 만 쓴다. Epic 은 파트 태그 없이 기능 이름만 쓴다. 공통 기획·설문·브랜딩·운영 문서는 `[DOC]`, 파트별 설계 문서는 해당 파트 태그를 쓴다.

이전 게임 프로젝트의 `[GD]`는 신규 이슈에서 사용하지 않는다. 진행할 기존 이슈는 현재 범위에 맞춰 제목·컴포넌트·완료 조건을 수정하고, 제외할 일은 사유를 남겨 백로그에서 분리한다. 완료된 과거 이슈는 당시 기록을 유지한다. Jira의 `IOT` 컴포넌트는 팀장이 실제로 추가하며, 문서 수정만으로 설정이 생성되지는 않는다.

나쁜 예:

```
매칭
동기화 작업
가입 UI 수정함
```

좋은 예:

```
[AI] 자연어 이상형 입력 구조화 구현
[BE] 만남 기록 양쪽 검증 구현
[FE] 가입 화면 필수 항목 검증 구현
[IOT] 키링 설정 저장 완료 응답 구현
```

### 제목은 동사로 끝낸다
_[title-verb]_

"구현", "연동", "작성", "수정", "조사" 처럼 끝낸다. 명사만 있는 제목은 끝났는지 판단할 수 없다.

### 버그 Story 제목은 증상을 쓴다
_[bug-title-symptom]_

`bug` 라벨을 단 Story 는 동사형 대신 관찰된 증상을 쓴다. 원인은 본문에 쓴다.

```
[BE] 상호 수락 전에 상대 프로필이 노출됨
```

## 컴포넌트와 라벨

### 모든 Story 에 컴포넌트를 하나 단다
_[one-component]_

Story의 컴포넌트는 제목의 파트 태그와 같다: `AI` `BE` `FE` `IOT` `INFRA` `DOC`. 여러 파트를 묶는 Epic에는 단일 파트 컴포넌트를 강제하지 않는다.

### 라벨은 정해진 것만 쓴다
_[fixed-labels]_

Story 의 종류를 나타내는 라벨은 하나만 단다. 아무것도 없으면 기능 개발 Story 다.

| 종류 라벨 | 의미 | 예시 |
| --- | --- | --- |
| (없음) | 사용자가 이용하는 앱·서버·키링 기능 | 익명 제안 수락, 키링 알림 구현 |
| `task` | 기능 구현 외의 설정·조사·문서·설문·디자인·홍보 작업 | API 명세 작성, 설문 배포, 로고 제작 |
| `bug` | 이미 완료된 기능이 의도와 다르게 동작 | 상호 수락 전에 프로필이 노출됨 |

상황 라벨은 해당할 때 추가로 단다.

| 상황 라벨 | 의미 | 다는 시점 |
| --- | --- | --- |
| `blocked` | 다른 이슈나 외부 요인 때문에 멈춤 | 막힌 날 즉시. 원인 이슈를 "blocks" 링크로 연결 |
| `contract` | 파트 간 API·메시지·매칭 계약의 최초 작성 또는 변경 | 앱↔서버, 서버↔AI, 앱↔키링, 키링 간 형식·공통 매칭 규칙을 정의하거나 바꿀 때 |
| `experiment` | 결과가 불확실한 조사·비교 | 모델 비교, 프롬프트 A/B |
| `demo` | 시연에 꼭 들어가야 하는 것 | 발표 시나리오에 나오는 기능 |
| `mentor` | 멘토·코치 피드백으로 생긴 일 | 미팅에서 나온 요청 |

새 라벨이 필요하면 팀 합의 후 이 표에 먼저 추가한다.

### `contract` 이슈는 관련 파트 담당자를 모두 Watcher 로 추가한다
_[contract-watchers]_

이슈 본문에 명세 경로·영향 파트·검토 담당자를 적고, 작성자가 관련 파트의 Watcher 등록과 MR 리뷰 요청을 확인한다. Watcher를 추가할 권한이 없으면 본문에 대상자를 기록하고 팀장에게 등록을 요청한다. 구독만으로 승인을 대신할 수 없으며, 승인 인원과 교차 리뷰 기준은 [GitLab 컨벤션](gitlab-convention.md)의 `[mr-approval]`을 따른다.

공통 명세는 `docs/contracts/api/`, `docs/contracts/keyring/`, `docs/contracts/matching/`에 두며, 최초 명세 작성 시 해당 파일을 만든다. 버전·필드·정상 및 오류 샘플·호환성·적용 순서와 변경 공유는 같은 문서의 `[shared-contracts]`를 따른다. 선행 계약이 정해지지 않아 구현이 멈췄다면 `blocked`와 의존 이슈를 기록한다.

## 스토리 포인트

### 1포인트는 30분 안에 끝나는 일이다
_[point-unit]_

피보나치 값 1, 2, 3, 5, 8 만 쓴다. 포인트는 난이도를 나타낸다. 걸리는 시간과 함께 모르는 부분이 얼마나 있는지, 다른 파트와 맞춰야 하는지를 보고 정한다.

| 포인트 | 시간 | 난이도 기준 | 예시 |
| --- | --- | --- | --- |
| 1 | 30분 이내 | 할 일과 방법이 명확함 | 문구 수정, 설정값 변경 |
| 2 | 1~2시간 | 방법을 알고 있고 수정 범위가 작음 | 단순 API 엔드포인트 하나 |
| 3 | 반나절 | 약간의 판단이나 조사가 필요함 | 화면 컴포넌트 하나 + API 연동 |
| 5 | 하루 | 설계가 필요하거나 다른 파트와 맞춰야 함 | 만남 기록 양쪽 검증 구현 |
| 8 | 2~3일 | 모르는 부분이 많고 조사·실험이 필요함 | 키링 간 발견·인증 통신 검증 |

### 시간과 난이도가 다른 등급을 가리키면 높은 쪽을 고른다
_[point-take-higher]_

예를 들어 1시간이면 끝나지만 다른 파트와 계약을 맞춰야 하는 일은 2가 아니라 5다.

### 8포인트를 넘는 일은 Epic 으로 만들고 하위 Story 로 나눈다
_[epic-over-eight]_

13 이상은 쓰지 않는다. 8포인트를 넘는 일은 Story 가 아니라 Epic 으로 만들고, 결과 단위의 하위 Story 로 나눈다. 하위 Story 는 각각 8포인트 이하여야 한다.

나쁜 예:

```
Story  [AI] 자연어 기반 매칭 파이프라인 구현        13점
```

좋은 예:

```
Epic   자연어 기반 매칭                          (포인트 없음)
 ├ Story  [AI] 자연어 이상형 구조화 구현          5점
 ├ Story  [AI] 양방향 선호 계산 구현              5점
 └ Story  [AI] 후보 모델 구조화 품질 비교 (task)   5점
```

### Epic 에는 포인트를 주지 않는다
_[no-points-on-epic]_

포인트는 하위 Story 에만 준다. Epic 의 규모는 하위 Story 포인트 합계로 본다. Epic 에 포인트를 주면 하위 Story 와 이중으로 계산되어 스프린트 용량이 틀어진다.

### 중요도는 포인트가 아니라 Priority 필드로 표시한다
_[priority-not-points]_

포인트에 중요도를 섞으면 주간 용량 계산이 틀어진다. 중요도는 Jira Priority 필드로 따로 단다.

| Priority | 기준 |
| --- | --- |
| Highest | 이게 안 되면 시연이나 다른 사람 작업이 막힘 |
| High | 이번 스프린트 목표에 직접 필요함 |
| Medium | 이번 스프린트에 하면 좋음 (기본값) |
| Low | 여유가 있을 때 |

계획 회의에서는 Priority 가 높은 순으로 용량이 찰 때까지 담는다.

### 포인트는 계획 회의에서 확정하고 스프린트 중에는 바꾸지 않는다
_[point-frozen]_

개인당 주간 용량은 약 20포인트를 초기 참고값으로 잡고, 1~2주 차 실측으로 조정한다. PM·팀장 업무, 리뷰·회의, 실기기 준비 시간을 고려해 각자의 계획 용량을 정하며, 포인트를 개인 성과 비교 기준으로 사용하지 않는다.

## 워크플로

### 상태는 해야 할 일, 진행 중, 완료 3개만 쓴다
_[three-states]_

Jira 워크플로의 상태 이름도 한글로 설정한다. 리뷰 단계는 따로 두지 않고, MR 리뷰 중인 이슈도 진행 중에 둔다.

| 상태 | 영문 (기본 워크플로) | 의미 |
| --- | --- | --- |
| 해야 할 일 | To Do | 스프린트에 들어온 일 |
| 진행 중 | In Progress | 구현·조사·제작·검토 중, MR 리뷰 대기 포함 |
| 완료 | Done | `[definition-of-done]` 또는 `[non-code-done]` 완료 기준 충족 |

```
해야 할 일 → 진행 중 → 완료
```

막힌 이슈는 상태를 바꾸지 않고 `blocked` 라벨만 단다.

### 상태는 담당자가 옮기고, 퇴근 전에 실제와 맞춘다
_[daily-sync]_

### 코드·저장소 문서·공통 계약은 MR 병합과 완료 조건을 모두 충족해야 완료다
_[definition-of-done]_

아래를 모두 만족해야 완료다. MR 병합만으로 설문 배포·실기기 검증 등 남은 완료 조건이 충족되는 것은 아니다. 자동 완료가 설정·검증되어 있고 이 MR로 모든 완료 조건을 충족할 때만 `Closes S15P31E106-번호` 를 쓴다 ([GitLab 컨벤션](gitlab-convention.md) `[mr-jira-sync]`).

- 이슈의 완료 조건을 모두 확인함
- MR 이 승인되어 `develop` 에 머지됨
- 다른 파트가 쓰는 API·메시지·매칭 계약을 처음 작성하거나 변경했다면 명세와 샘플을 갱신하고 필요한 파트의 승인을 받음
- AI 구조화·매칭 관련 기능은 정상·누락값·조건 충돌을 포함한 최소 3개 사례의 입력, 기대 결과, 실제 결과, 모델·프롬프트·규칙 버전을 이슈 또는 연결된 검증 자료에 남김
- IoT 작업은 가상 검증과 실기기 검증을 구분하고, 이슈에 실기기 검증이 요구되면 보드·펌웨어 버전과 실행 결과를 남김. 가상 키링 통과만으로 실기기 검증을 완료 처리하지 않음

### 저장소 변경이 없는 설문·디자인·운영 작업은 결과물과 검토 기록으로 완료한다
_[non-code-done]_

계획 시 Story 본문에 완료 방식(`MR 병합` 또는 `결과물 검토`), 결과물 위치, 작성자가 아닌 검토자를 적는다. 코드·설정·저장소 문서·공통 계약의 변경은 반드시 MR을 사용하며, 결과물 검토 방식으로 우회하지 않는다.

| 작업 | 필요한 증거 예시 |
| --- | --- |
| 설문 문항 작성 | 검토 가능한 설문 최종본, 문항 검토 기록 |
| 설문 배포·분석 | 배포 대상·기간·배포 확인, 익명화한 집계·분석 결과 |
| 화면 설계·로고·홍보물 | 팀이 접근 가능한 최종 디자인 링크·버전 또는 내보낸 파일, 검토 기록 |
| 운영·조사 | 결정 사항·근거·후속 작업이 포함된 문서 또는 결과 기록 |

이슈의 완료 조건을 모두 충족하고 결과물 링크·버전 또는 기준일·검토자의 승인 기록을 남기면 담당자가 수동으로 완료 처리한다. 외부 결과물은 팀원 접근 권한과 변경 이력을 확보한다. 설문 원본 개인정보·실사용자 프로필은 저장소와 공개 이슈에 올리지 않는다. 저장소 변경과 외부 실행이 모두 포함된 Story는 MR 병합과 외부 결과물 검토가 모두 끝나야 완료다.

## 스프린트

### 스프린트는 월요일에 시작해 금요일에 끝나는 1주 단위다
_[weekly-sprint]_

이름은 `S1`~`S6` 과 주차 목표 한 줄로 짓는다. 예: `S2 수직 슬라이스`.

| 언제 | 무엇을 | 시간 |
| --- | --- | --- |
| 월요일 오전 | 계획: 목표 한 줄, 이슈 선정, 포인트 확정 | 30분 |
| 매일 오전 | 스탠드업: 어제 한 것, 오늘 할 것, 막힌 것 | 15분 |
| 금요일 오후 | 리뷰(동작 시연) + 회고, 미완료 이슈 이월 결정 | 1시간 |

### 스프린트 중 이슈를 추가하면 같은 포인트만큼 뺀다
_[sprint-scope-swap]_

단, `bug` 라벨 Story 는 바로 추가한다.

### 멘토·코치 보고는 매주 한 줄로 한다
_[weekly-report]_

스프린트 보고서의 숫자를 그대로 쓴다.

```
S2: 이번 주 할 일 14개 중 12개 완료 (완료 98/115점). 미완료 2개는 키링 부품 도착 대기로 S3 이월.
```

## 이슈 본문

### Story 본문에는 목적과 완료 조건을 쓴다
_[story-template]_

완료 조건이 비어 있으면 스프린트에 넣지 않는다.

```markdown
## 목적
사용자(또는 팀)가 무엇을 할 수 있게 되나, 한두 문장

## 완료 조건
- [ ] 확인 가능한 결과 1
- [ ] 확인 가능한 결과 2

## 결과물·검토
- 완료 방식: MR 병합 / 결과물 검토 (둘 다 필요한 경우 함께 기재)
- 결과물 위치:
- 검토자:
- 영향 파트·명세 버전 (contract 해당 시):

## 참고
관련 이슈, 문서, 디자인 링크
```

### 버그 Story 본문에는 재현 순서를 쓴다
_[bug-template]_

`bug` 라벨 Story 는 위 템플릿 대신 아래를 쓴다.

```markdown
## 증상
무엇이 어떻게 잘못 되는가

## 재현 순서
1.
2.

## 기대 동작 / 실제 동작

## 환경
브랜치·커밋, 앱·OS·기기·펌웨어 버전, 익명화한 이벤트 ID, 로그·스크린샷
```

### AI·매칭·기기 연동 버그에는 입력과 상태 변화를 첨부한다
_[attach-matching-log]_

AI·매칭 버그는 익명화한 입력, 구조화 결과, 기대·실제 판정, 모델·프롬프트·규칙 버전을 남긴다. LLM 출력은 같은 입력으로도 달라질 수 있으므로 당시 결과를 보존한다. 기기 연동 버그는 이벤트 ID, 송수신 메시지, 시각·연결 상태·재시도 순서를 남긴다. 비밀키·인증 토큰·개인정보는 로그에서 제거한다.

## 운영 설정 반영

팀장은 `IOT` 컴포넌트, 현재 파트 표기, Watcher 권한, GitLab 보호 브랜치·리뷰·Jira 전환 설정을 확인하고 관련 운영 이슈에 확인일·확인자·결과를 남긴다. PM은 진행할 기존 이슈의 범위·담당·완료 조건을 현재 서비스에 맞춘다. 문서 개정과 실제 도구 설정 완료는 구분하며, 미반영 항목은 담당자와 목표일을 지정해 추적한다.
